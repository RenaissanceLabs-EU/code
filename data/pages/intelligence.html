What it means to compute

In 1936, before any electronic computer existed, Alan Turing asked what it means to follow a rule mechanically. His answer was an imaginary machine: a strip of tape, a head that reads and writes one symbol at a time, and a finite table saying what to do next. In the same year Alonzo Church gave a completely different answer, a notation for functions called the lambda calculus. The two turned out to compute exactly the same things.

So has every reasonable definition proposed since. The claim that they always will, that anything computable by any mechanical procedure is computable by a Turing machine, is the Church-Turing thesis. It cannot be proved, because "mechanical procedure" is an informal idea, but nothing has contradicted it in ninety years.

Turing's paper contained a second idea that matters as much. One particular machine can read the description of any other machine from its tape and imitate it. This is the universal machine, and it is the theoretical basis of software. A computer does not have to be built for a task. It is built once, to run programs, and the task arrives later as data. Every level of the stack on this site is that idea applied again.

Simple rules are enough

A universal machine does not need to be complicated. Take a row of cells, each black or white. To get the next row, every cell looks at itself and its two neighbors and consults a table with eight entries. That table is the whole program. There are 256 possible tables, and one of them, called Rule 110, has been proved able to carry out any computation, given a suitable starting row of unlimited length.

The lesson reaches well beyond toy systems. Rich behavior does not require rich ingredients. A handful of gate types is enough to build a processor, a few dozen instructions are enough to run any software, and one arithmetic pattern repeated billions of times is enough for a language model. What code adds is organization, layer upon layer of it.

What cannot be computed

The same 1936 paper showed that computation has a hard edge. There is no program that can look at any program and its input and correctly say whether it will ever finish. This is the halting problem (the name came later; Turing's own paper proved an equivalent result), and it is impossible in principle, however clever the method or fast the machine.

In 1953 Henry Rice proved something broader. Every interesting question about what a program does, as opposed to how it is written, is undecidable in the same way. Does it ever print a 7? Does it compute the same function as this other program? Is it free of some bug? No program can answer any such question correctly for all programs.

This theorem is one reason for the shape of software engineering. Because no perfect checker can exist, every real checker gives something up. A type system refuses some correct programs. Tests examine a few inputs and stay silent on the rest. A proof settles the question completely, but a person or a model has to find the proof, and there is no guarantee one will be found. The ladder of checks on this site is a set of different bargains with the same impossibility.

Whether this loop finishes for every starting number is the Collatz conjecture, open since the 1930s. Its halting is an open problem, and slightly more general loops of this kind are provably undecidable. A question about three lines of code has resisted the whole of mathematics. Reading code is not the same as knowing what it does.

Programs and proofs are the same thing

There is an exact correspondence between logic and programming, noticed in pieces by Haskell Curry and William Howard. A type can be read as a proposition. A program of that type is a proof of the proposition. A function that turns any value of type A into a value of type B is a proof that A implies B, and running the program is the same as simplifying the proof.

This is not an analogy. Proof assistants such as Lean are programming languages in which the correspondence is used directly: to prove a theorem you write a program, and the type checker accepts it only if the proof is valid. It is why the proof form of a program sits at the top of the ladder, and why our map of mathematics and this map of code are two views of one subject. Mathematics is the part concerned with what is true. Code is the part that also has to run.

Programs that are found instead of written

For most of the history of computing, every program was written by a person who understood, at least locally, why each line was there. Machine learning breaks that link. Training is a search through an enormous space of possible programs, guided only by how well each candidate fits the examples. What comes out is a program in the strict sense, but one with no author and no explanation. The learned programs level of the stack lets you watch a very small one being found.

Such programs can do things nobody knows how to write by hand, including understanding language. They also give up the property that made software trustworthy: that someone could read it. A network's weights can be executed and tested. They cannot in general be reviewed or proved correct, though specific properties of small networks can be verified. Interpretability research is the effort to recover that ability.

Why it matters that models write code

When a model answers a question, you receive an answer, and you have to decide how far to trust it. When a model writes a program, you receive something of a different kind. The program can be read. It can be parsed, type-checked, run against tests, and in the best case proved. It can be kept, versioned and executed a billion times without the model being involved again.

Code is therefore the place where learned ability turns back into explicit, checkable structure. Everything on this site about the forms of a program is, from this angle, a description of the instruments available for inspecting what a model produces. That is the practical reason code is the best understood subject for training: the feedback is automatic and, when the checks are good, exact.

It also moves the bottleneck. Writing code was slow and checking it was slower. Models make writing fast. What limits the amount of trustworthy software is now verification: tests that cannot be gamed, specifications that say what is meant, and proofs where the stakes justify them. A society that runs on code will be shaped by how well that checking is done.

Structure that exists outside of minds

Writing let knowledge outlive the person who had it. Mathematics let reasoning be checked by someone else. Code added a third thing: knowledge that carries itself out. A program is a piece of understanding that has been made precise enough to act without the person who understood it, and to keep acting, unchanged, for as long as a machine will run it.

That is what makes code more than a tool for engineers. It is the medium in which a civilization stores procedures it can no longer afford to perform by hand, and now it is the medium in which artificial minds are built and in which they do much of their work. Understanding it, from the transistor to the trained model, is part of understanding how intelligence of any kind gets built and kept.
