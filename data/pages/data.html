A model learns what its data and its feedback reward. So the choice of data is the choice of behavior: raw code teaches what code looks like, instruction pairs teach how to answer a request, tests teach what works. This page lays out the main kinds of data side by side, says what each one teaches, and shows how the conceptual forms of a program on this site map onto training signals.

2. The tradeoffs, one by one

Every dataset decision trades five things against each other. Name which one you are paying for.

Quality you wantWhat buying it costsWhat to do
VolumeMore tokens means more compute, and past a point repeats and near-copies dominate. Volume alone does not teach tasks that the data does not contain.Deduplicate first. For fine-tuning, start with thousands of examples, not millions, and add more only where evaluation shows a gap.
QualityFiltering throws data away, and strict filters can remove the variety that makes a model robust. The OpenCoder study trained two 1.5B models and found that keeping only repositories with at least 5 stars did worse than keeping all of them, which the authors attribute to lost diversity.Filter for defects you can name (broken, generated, unsafe, duplicated). Check what the filter removed by reading samples.
DiversityWide coverage costs effort to collect and can dilute a narrow target.Diversity of problems can matter more than verifying each solution. The OpenCodeReasoning authors found that, in one setup, filtering to solutions that pass tests scored lower than keeping all of them, and that adding more unique questions gave the largest gains.
DifficultyHard problems are costly to write and to check, and with group-based RL such as GRPO, a model that fails every sample learns nothing from that problem.For RL, keep a middle band the model sometimes solves. For SFT, mix easy and hard, since the easy ones set the format.
RelevanceData close to your target helps most and is least available. Data far from it is plentiful and may do nothing for the task.Evaluate on data like your target. Spend your effort on a small set that matches it.

3. Make the connection explicit

Write one line for each data source you consider: this data gives the model this signal, which I expect to improve this behavior, and I will check it with this test. If any part of the sentence is missing, you do not yet know why the data is in the mix.

  • Examples: "Function-level instruction pairs with unit tests teach the model to write complete, runnable functions; I expect HumanEval+ to rise; I will also check that a held-out set of my own tasks improves."
  • "Issue-patch pairs teach small, local edits tied to a reason; I expect repair benchmarks to improve and long-context completion to be unchanged; I will check both."
  • "Reasoning traces from a stronger model teach longer working before the answer; I expect hard-problem accuracy to rise and answers to get longer; I will check cost per answer."

The stack levels matter too. Data is plentiful for languages and applications and thin for hardware, machine code and infrastructure, as the stack map shows in its resource counts. If your target is low in the stack, plan to build your own data.
