Evaluation is not the last step. It is how every earlier step gets decided. Without a fixed measurement before you start, you cannot say whether a change to the data, the method or the hyperparameters helped. This page lays out what to measure, how to run it safely, and where the standard benchmarks mislead.

1. Decide the tests before you train

Four kinds of check belong in every project. Set them up first, run them on the model you start from, and keep the numbers.

CheckQuestion it answersHowResources
Held-out evaluationDoes it work on problems it has not seen?A split of your own data that was never in training, split by repository or problem group so that related items stay together. Plus a public benchmark that fits your capability.{{r:evalplus-humanevalplus}}, {{r:livecodebench}}, {{r:bigcodebench}}
Execution-based correctnessDoes the code run and give the right answer?Run each generated solution against tests in a sandbox. Report pass@1 with a fixed sampling setup, not one lucky run.{{r:evalplus-cli}}, {{r:sb-bigcode-eval}}

2. Report results so they can be trusted

  • Pin everything. Harness version, prompt template, sampling temperature, number of samples, seed, maximum length, dataset version. Different harnesses give different numbers for the same model.
  • State k. pass@1 and pass@10 are different claims. The estimator is short, and the figure on the training page lets you see how a solved-1-in-5 problem looks at each k.
{{snip:pass-at-k-unbiased}}
  • Use more than one sample. Report pass@1 from several samples per problem, and a confidence interval or the spread across seeds. A difference of one or two points on a benchmark with a few hundred problems is within noise.
  • Read failures by hand. Some benchmark items have flawed tests or ambiguous statements. A sample of failures tells you more than a score.
  • Compare like with like. Same prompt, same harness, same settings for the base and the tuned model.

3. Benchmark limits and contamination

Public benchmarks are useful and unreliable in known ways.

  • Contamination. If a benchmark's problems or solutions appear in training data, the score measures memory. This is easy to cause by accident, because benchmark problems are copied across the web and repositories. Remove benchmark problems and near-copies from the training set, and confirm with an evaluation that cannot have been seen, such as {{r:livecodebench}}, which records release dates so you can score only problems published after the model's training cutoff.
  • Rephrased copies slip through. Plain n-gram matching misses paraphrases ({{r:paper-rephrased-contamination}}). Use a held-out set of your own as the number you trust most.
  • Weak tests. The original HumanEval tests accepted wrong programs, which is why {{r:evalplus-humanevalplus}} adds many more. {{r:swe-bench-verified}} is still widely reported, but OpenAI stopped using it in February 2026 because of flawed tests and contamination, so treat its numbers as upper bounds and add a contamination-resistant set such as {{r:swe-bench-live}}.
  • Saturation. When most models score near the top, the benchmark no longer separates them. Move to a harder one.
  • Task mismatch. A function-writing benchmark says little about repository work or tool use. Use the benchmark that matches the capability you chose.

4. Run generated code in isolation

Model output is untrusted code. Never run it on your own machine's account. Run it in a container or virtual machine with no network, a read-only file system apart from a scratch directory, limits on memory, processes and time, and no secrets in the environment. Keep the tests out of the model's reach, since a model that can read or edit them will.

5. Evaluation inside the training loop

  1. Baseline

    Run all four checks on the starting model. Save the outputs, the settings and the harness version.

  2. Small experiment

    Train on a small slice for a short run. Re-run the fast checks. If nothing moves, the problem is the data or the objective, not the scale.

  3. Compare per task

    Look at which tasks went from fail to pass and which went the other way. Gains that all come from one task family point to leakage or a narrow fix.

  4. Gate

    Before any larger run, require the held-out score to improve, regressions to stay within a threshold you set in advance, and a sample of passing outputs to look correct when read.

  5. Repeat with one change

    Change one thing at a time: the data, the filter, the learning rate. Record each run's settings and results in the experiment tracker.

The first training run applies this loop to a small fine-tune end to end.
