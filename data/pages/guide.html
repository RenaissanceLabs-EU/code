You do not need a frontier lab to make a model better at code. You need a loop you can trust. This guide is the short version of what the published evidence and the open tooling support, with the caveats attached. Every dataset and tool named here is in the catalog with its license and limits. If you would rather answer a few questions and get a plan, use the recipe builder.

The loop1. Measure with an eval the model cannot have memorized. 2. Fix data quality. 3. Teach the format with SFT. 4. Reward what passes tests (RL with verifiable rewards). 5. Measure again with the same settings. Change one thing at a time.

0. Decide what “better” means

“Good at code” is at least five different skills: completing the next lines, writing a function from a description, fixing a bug in a repository, working in a terminal, and writing SQL. They need different data, different evals and different verifiers. Write down one sentence, such as “resolve more real GitHub issues in Python repositories”, and let it choose your eval. Everything below depends on that sentence.

1. Measure first

Before you change anything, score the model you have. This is the step people skip, and it is the one that makes every later decision honest.

  • Use at least one eval the model cannot have seen. Classic benchmarks such as HumanEval have been public for years and leak into training sets. {{r:livecodebench}} collects new problems with release dates, so you can score only problems published after your model’s training cutoff. For repository tasks, {{r:swe-bench-live}} and {{r:swe-rebench}} refresh over time. Be careful with the best-known repository benchmark: OpenAI reported in February 2026 that it had stopped reporting {{r:swe-bench-verified}} after finding many problems with flawed tests or descriptions and signs of training exposure. Use it to compare with published numbers, not as your only gate.
  • Match the eval to your sentence. Function writing: EvalPlus-style tests. Repository work: SWE-bench-style tasks. Terminal work: {{r:terminal-bench-2}}.
  • Freeze the settings. Same prompt format, same sampling temperature, same number of samples, same harness version. Different harnesses give different numbers for the same model.
  • Report pass@1 from several samples, not one lucky run. The unbiased estimator is short:
{{snip:pass-at-k-unbiased}} {{snip:livecodebench-runner}}

Keep one private eval. Fifty to two hundred tasks from your own domain, with tests, never published, never used for training. It is the only number you can fully trust.

Also read failures by hand. Some benchmark instances have flawed tests or ambiguous statements, so a small difference on a single benchmark is easy to over-read.

2. Fix data quality

If you only change the data, you can still move a model a long way. Three things come first.

  • Deduplicate. Near-duplicate files inflate scores and waste training tokens. {{r:datatrove}} implements MinHash deduplication that you can run locally.
  • Decontaminate. Remove anything that overlaps your eval sets. Plain n-gram matching misses rephrased copies (a 2023 study, arXiv 2311.04850, showed this), which is another reason to keep a private eval and a time-windowed one.
  • Mind licenses. Code corpora carry per-file licenses, and synthetic datasets inherit the terms of the model that wrote them. Keep the metadata.
{{snip:datatrove-minhash}}

For pretraining-scale data, quality filtering has repeatedly beaten raw volume for smaller models. {{r:stack-edu}} and {{r:the-stack-v3-train}} are the open starting points; {{r:opencoder-repo}} is the most transparent end-to-end recipe. Most readers will not pretrain. They will use this stage to clean their own SFT and RL data.

3. Teach the format with SFT

Supervised fine-tuning is cheap and fast to iterate. It teaches the model to follow instructions, explain, edit and call tools. Start small, because published results suggest that a few tens of thousands of carefully seeded, checked examples compete with much larger sets: the Magicoder paper (arXiv 2312.02120) used 75K examples from {{r:magicoder-oss-instruct-75k}}, and SelfCodeAlign (arXiv 2410.24198) used 74K self-generated, execution-validated pairs.

  • Short answers and edits: {{r:magicoder-oss-instruct-75k}}, {{r:opencodeinstruct}}, {{r:commitpackft}}.
  • Hard reasoning: distilled traces such as {{r:opencodereasoning}}. One caution from that paper: the authors report that filtering traces by execution hurt benchmark accuracy, so diversity of problems mattered more than verifying every trace. Treat it as a reason to run your own ablation, not as a rule.
  • Repository and agent work: trajectories such as {{r:swe-smith-trajectories}} and {{r:nebius-swe-rebench-openhands-trajectories}}. Match the harness you will deploy with, because trajectories encode its tool format.
{{snip:trl-sft-python}}
Check teacher termsMany synthetic sets were written by proprietary or open-weight teachers. Their cards name the teacher, and some are non-commercial. Look at the license and the caveats on each resource page before you train a model you plan to ship.

4. Preference data (optional)

Preference optimization is useful when SFT has plateaued and you want a cheap step before RL. Pairs derived from test results are far more reliable than pairs picked by another model. AceCoder (arXiv 2502.01718) built pairs from test cases and reports gains from both reward models and RL; its data is in {{r:acecode-v2-122k}}. If you can run tests, building on-policy pairs from your own model’s samples is often a better use of your time than a public set. Control for length, or the model learns that longer is better.

5. Reward what passes: RL with verifiable rewards

Code is one of the few domains where you can check the answer by running it. That is the idea behind RL with verifiable rewards: sample several solutions per task, run the tests, reward the ones that pass. Open recipes such as DeepCoder (14B model card) and Skywork-OR1 (arXiv 2505.22312) report gains this way. The hard part is not the algorithm. It is the verifier.

Pick the task source to match the verifier

  • Function problems with tests: {{r:kodcode}} (pytest, but check its non-commercial license), {{r:acecode-v2-122k}}.
  • Competitive programming: {{r:deepcoder-preview}}, {{r:skywork-or1-rl-data}}. The verifier runs stdin and stdout tests in a sandbox.
  • Repository issues: {{r:swe-gym}}, {{r:swe-smith}}, {{r:r2e-gym}}, {{r:swe-rebench}}. Each task has a container image. Reward is: the target failing tests now pass and the passing tests still pass.
  • Terminal tasks: Harbor-format tasks via {{r:harbor}}.

Keep a middle band of difficulty

With group-relative methods such as GRPO, a task where every sampled solution gets the same reward teaches nothing. Tasks the model always solves or never solves are wasted compute. Slide the figure to see how fast the useful fraction collapses at the extremes.

{{fig:grad}}

In practice, sample your own model several times per task and keep tasks with mixed outcomes. Some datasets ship difficulty fields you can use as a first filter. DeepCoder’s card also describes filtering overlong and truncated samples.

Start from a model that already solves some tasks

The published open recipes start from strong distilled or instruct models (DeepCoder, AceReason and Skywork-OR1 all start from R1-distilled bases). From a weak start, most rollouts fail and the signal is thin. Do SFT first.

Build the verifier like an adversary is attacking it

One is. Models optimize whatever you reward. Documented cases include reading the future fix from git history, editing the tests, and fetching solutions from the web. See pitfalls. The minimum:

  • Run generated code in a container with no network, a read-only filesystem, and memory, CPU and process limits.
  • Put the tests in after the agent finishes, from outside the sandbox. Never leave them where the agent can read or edit them.
  • Strip future git history from repository tasks.
  • Check each task with a reference solution: it must pass, and the unfixed code must fail.

For larger runs, use a framework built for rollouts, such as {{r:fw-verl}}. {{r:fw-trl}} is fine for small experiments.

6. Re-measure, and keep what helped

Run the same evals with the same settings. Look at three things: the target score, a general-coding regression check (RL on competitive problems can hurt other behavior), and a handful of outputs read by eye. If something got worse, undo the last change before adding another.

What we know, and what we do not

  • Well supported: contamination inflates classic benchmarks; deduplication and quality filtering help; small checked SFT sets are competitive; test-verified RL moves reasoning and repository scores for models that start strong; verifiers get hacked.
  • Contested: whether large-scale RL beats distillation for small models. The OpenCodeReasoning paper (arXiv 2504.01943) reports strong SFT-only results, while AceReason (arXiv 2505.16400) argues large RL can go further. Run both at your scale if it matters.
  • Not known to us: the right data mixture for your base model and language mix. No page can tell you that. Your private eval can.

Numbers quoted on resource pages come from the cited source on the check date. Benchmarks and leaderboards move fast, so confirm any score at its source.
