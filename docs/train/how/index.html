How a code model is trained

From a pile of public source code to a model that fixes issues in a real repository: the stages, what each one does, where the data comes from and where it goes wrong. With working figures and the resources for each step.

Compare open code modelsReading listRecipe builder

The idea in one paragraph

A coding model is a language model that has been through several stages. The first stage teaches it what code looks like by having it predict the next piece of text across billions of files. The next stages teach it what to do with that knowledge: follow an instruction, explain, edit, call tools. The last stage lets it try, runs what it wrote, and rewards what works. Each stage changes what the model has seen and what it is rewarded for, and each has its own data, its own checks and its own ways to go wrong.

The forms of a program explain why this works so well for code. Every form is a check a machine can run, so the model can be given feedback without a person in the loop. The stages below are, in order, a way of turning more and more of those checks into training signal.

Stage 1. Pretraining on code

The model reads public source code and learns to predict what comes next. The raw material is mostly the open repositories of the world: The Stack v2, the dataset behind StarCoder2, is built on the Software Heritage archive, and the StarCoder2 training set adds GitHub issues, pull requests, notebooks and documentation to it. The work is in what is thrown away. Files are filtered by license, by quality and by language, duplicates and near-duplicates are removed, personal data and secrets are scrubbed, and anything that overlaps with an evaluation set is taken out. Several recent recipes add a quality classifier on top: Stack-Edu keeps the files that a classifier, trained on an LLM's 0 to 5 educational ratings, scored 3 or higher, in 15 languages, and the SmolLM2 team found that this improved MultiPL-E scores in most languages in short annealing runs. The OpenCoder authors report a related result for the final annealing phase: removing its high-quality data lowered scores a lot.

Plain next-token prediction only writes forward. Real editors need completion in the middle of a file, so many code models, including StarCoder, StarCoder2 and DeepSeek-Coder, are also trained with fill in the middle: a stretch of the file is cut out, moved to the end, and marked with special tokens, so that the model learns to write the missing piece given the code before and after it. Bavarian and colleagues at OpenAI showed that this can be added with little or no cost to ordinary left-to-right ability.

Near the end of pretraining, many teams switch to a smaller, cleaner mix, often with more synthetic and educational data, and then lengthen the context window so that the model can read several files or a whole repository at once. The details differ by model. The comparison of open code models sets them side by side.

Stage 2. Supervised fine-tuning

A pretrained model continues text. It does not yet answer questions or follow instructions. Supervised fine-tuning shows it examples of an instruction and a good response, and trains it to produce the response. For code the question is where good examples come from, because humans rarely write them at scale.

  • Synthetic instructions. A stronger model writes the examples. Magicoder's OSS-Instruct starts from real snippets of open code and asks a model to invent a problem and solution inspired by each (Magicoder OSS-Instruct 75K). Evol-Instruct makes existing instructions progressively harder (Evol-CodeAlpaca v1).
  • Examples that were run. The solution is executed against tests and kept only if it passes. KodCode-V1 was built this way, with unit tests for every problem.
  • Reasoning traces. A strong reasoning model writes out its working before the answer, and the smaller model learns from those traces: OpenCodeReasoning, open-r1 CodeForces-CoTs.
  • Agent trajectories. For repository tasks the examples are whole sessions: reading files, running commands, editing, running tests. SWE-smith trajectories and SWE-Gym OpenHands sampled trajectories are open sets.

Two practical rules recur across the recipes. Most tooling computes the loss on the response only, not on the instruction, though some work finds that including the instruction helps when responses are short. And check the terms of the teacher model and the license of the source problems as well as the dataset's own license: they can differ.

Stage 3. Preference data

Preference training teaches a model which of two answers is better. For code, the cleanest pair is one answer that passes the tests and one that fails, which needs no human judge. Direct preference optimization (DPO) then trains the model to prefer the first. Some recipes train a reward model on such pairs instead, and a few (AceCoder) build the tests themselves with a model. Pairs from an LLM judge are cheaper but reward style and length, so they are usually controlled for both.

Many current recipes skip this stage and go straight to the next one, because a test suite can serve as the reward directly.

Stage 4. Reinforcement learning with verifiable rewards

For hard problems, large gains often come from reasoning-trace fine-tuning first, and this stage adds further gains on top, because it trains directly on whether the code passes. The loop is short. The model writes several solutions to each problem, a sandbox runs them against the tests, passing solutions get reward 1 and failing ones 0, and the model is updated to make the winning kind of answer more likely. Methods such as GRPO make this work without a separate value model by comparing the samples for one problem against each other.

That comparison is why difficulty matters. If every sample for a problem passes, or every sample fails, there is nothing to compare, and the problem teaches nothing. RL task sets are therefore filtered to a middle band of problems the model sometimes solves. Open task sets for it range from competitive programming (DeepCoder-Preview-Dataset, KodCode-Light-RL-10K) to real repository issues with their tests (SWE-Gym, Multi-SWE-RL). Frameworks that run the rollouts include verl, TRL and SkyRL, and two complete public recipes are DeepCoder RL recipe (GRPO+) and DeepSWE RL recipe (rLLM).

The reward is only as good as the tests. Models find the gaps: they read the repository history or other files for the answer, edit or skip the tests, special-case the expected values, or look the fix up on the network if the sandbox leaves it on (Coding or Cheating?, Auditing Reward Hackability in Code RL Environments, and OpenAI's monitoring paper, arXiv 2503.11926). A sound setup keeps the tests out of the model's reach, runs everything in an isolated container with no network and strict limits, holds some tests back, and reads a sample of passing solutions by hand.

Evaluation, all the way through

You cannot tell whether a stage helped without a fixed measurement. Run a fast eval in minutes and a slower gate in hours, pin the harness and the prompt, and keep one private set that no one has published. Report how many samples you drew, not only the score.

Two failures spoil most numbers. Contamination: if the benchmark's problems or their solutions were in the training data, the score measures memory. LiveCodeBench fights it by adding new problems continuously and recording their release dates, so you can score only problems published after a model's training cutoff. Saturation: when every model scores near the top, the benchmark no longer separates them. Tests can also be weak. HumanEval+ (EvalPlus) exists because the original HumanEval tests accepted wrong programs.

A small team's path through the stages

A small team does not need to pretrain, and usually should not: the open code models were trained on trillions of tokens. They start from a strong open base model, build a small, carefully filtered SFT set with execution-checked examples, measure, and only then add RL on a task set filtered to a middle band of difficulty, with a sandbox they trust. That order is cheap to start and each step can be measured against the last.
