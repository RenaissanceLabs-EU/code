Evaluate as part of training

Evaluation is not the last step. It is how every earlier step gets decided. Without a fixed measurement before you start, you cannot say whether a change to the data, the method or the hyperparameters helped. This page lays out what to measure, how to run it safely, and where the standard benchmarks mislead.

1. Decide the tests before you train

Four kinds of check belong in every project. Set them up first, run them on the model you start from, and keep the numbers.

CheckQuestion it answersHowResources
Held-out evaluationDoes it work on problems it has not seen?A split of your own data that was never in training, split by repository or problem group so that related items stay together. Plus a public benchmark that fits your capability.HumanEval+ (EvalPlus), LiveCodeBench, BigCodeBench
Execution-based correctnessDoes the code run and give the right answer?Run each generated solution against tests in a sandbox. Report pass@1 with a fixed sampling setup, not one lucky run.EvalPlus CLI, bigcode-evaluation-harness
Repository-level tasksCan it work in a real codebase, with several files and its own tests?Issues with a container per task. Success means the failing tests now pass and the passing tests still pass.SWE-bench Verified, SWE-bench Multilingual, SWE-bench-Live
Regression checksDid training break something it used to do?Run the base model's strong benchmarks and a small set of general prompts before and after. Compare per-task results, not only averages.A frozen private set of 50 to 200 tasks from your own domain, plus a general chat check.

2. Report results so they can be trusted

  • Pin everything. Harness version, prompt template, sampling temperature, number of samples, seed, maximum length, dataset version. Different harnesses give different numbers for the same model.
  • State k. pass@1 and pass@10 are different claims. The estimator is short, and the figure on the training page lets you see how a solved-1-in-5 problem looks at each k.
Unbiased pass@k estimator
import numpy as np


def pass_at_k(n, c, k):
    """Unbiased pass@k estimator (Chen et al. 2021, Codex paper).

    n: samples generated per problem, c: samples that passed, k: budget.
    Computes 1 - C(n-c, k) / C(n, k) in a numerically stable product form.
    """
    if n - c < k:
        return 1.0
    return 1.0 - np.prod(1.0 - k / np.arange(n - c + 1, n + 1))


if __name__ == "__main__":
    from math import comb
    # tiny check against the exact combinatorial definition
    for n, c, k in [(10, 3, 1), (10, 3, 5), (200, 37, 10), (20, 0, 5), (20, 20, 5), (5, 1, 5)]:
        exact = 1.0 - comb(n - c, k) / comb(n, k) if n - c >= k else 1.0
        assert abs(pass_at_k(n, c, k) - exact) < 1e-12, (n, c, k)
    assert abs(pass_at_k(10, 3, 1) - 0.3) < 1e-12  # pass@1 is c/n
    print("ok", round(pass_at_k(200, 37, 10), 6))

Verified: ran locally, version seen: Python 3.9.6, numpy. Ran locally on Python 3.9 with numpy: matches the exact 1 - C(n-c,k)/C(n,k) definition for six cases, pass@1 equals c/n, and the check prints ok. Average the result over problems. Needs n >= k. source

  • Use more than one sample. Report pass@1 from several samples per problem, and a confidence interval or the spread across seeds. A difference of one or two points on a benchmark with a few hundred problems is within noise.
  • Read failures by hand. Some benchmark items have flawed tests or ambiguous statements. A sample of failures tells you more than a score.
  • Compare like with like. Same prompt, same harness, same settings for the base and the tuned model.

3. Benchmark limits and contamination

Public benchmarks are useful and unreliable in known ways.

  • Contamination. If a benchmark's problems or solutions appear in training data, the score measures memory. This is easy to cause by accident, because benchmark problems are copied across the web and repositories. Remove benchmark problems and near-copies from the training set, and confirm with an evaluation that cannot have been seen, such as LiveCodeBench, which records release dates so you can score only problems published after the model's training cutoff.
  • Rephrased copies slip through. Plain n-gram matching misses paraphrases (Rethinking Benchmark and Contamination (rephrased samples)). Use a held-out set of your own as the number you trust most.
  • Weak tests. The original HumanEval tests accepted wrong programs, which is why HumanEval+ (EvalPlus) adds many more. SWE-bench Verified is still widely reported, but OpenAI stopped using it in February 2026 because of flawed tests and contamination, so treat its numbers as upper bounds and add a contamination-resistant set such as SWE-bench-Live.
  • Saturation. When most models score near the top, the benchmark no longer separates them. Move to a harder one.
  • Task mismatch. A function-writing benchmark says little about repository work or tool use. Use the benchmark that matches the capability you chose.

4. Run generated code in isolation

Model output is untrusted code. Never run it on your own machine's account. Run it in a container or virtual machine with no network, a read-only file system apart from a scratch directory, limits on memory, processes and time, and no secrets in the environment. Keep the tests out of the model's reach, since a model that can read or edit them will.

Hardened Docker run for untrusted generated code
docker run --rm \
  --network none \
  --read-only \
  --memory 256m --memory-swap 256m \
  --cpus 1 \
  --pids-limit 64 \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --user 65534:65534 \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  -v "$PWD/job:/work:ro" -w /work \
  python:3.12-slim timeout 10 python candidate.py

A Docker container shares the kernel of the Linux host (or of Docker Desktop's Linux VM), so stronger isolation adds a user-space kernel such as gVisor or a microVM such as Firecracker. The tools directory lists the options. For RL, run the reward function inside the sandbox and return only a number. The snippet below limits time and resources but does not isolate anything by itself:

Reward function: run code plus tests in a subprocess with limits
import os
import subprocess
import sys
import tempfile

try:
    import resource  # POSIX only
except ImportError:  # pragma: no cover
    resource = None


def _limits(cpu_seconds, mem_bytes):
    def apply():
        if resource is None:
            return
        os.setsid()
        resource.setrlimit(resource.RLIMIT_CPU, (cpu_seconds, cpu_seconds))
        resource.setrlimit(resource.RLIMIT_FSIZE, (1 << 20, 1 << 20))
        resource.setrlimit(resource.RLIMIT_CORE, (0, 0))
        if sys.platform.startswith("linux"):  # RLIMIT_AS is unreliable on macOS
            resource.setrlimit(resource.RLIMIT_AS, (mem_bytes, mem_bytes))
            resource.setrlimit(resource.RLIMIT_NPROC, (64, 64))
    return apply


def run_tests(code, tests, timeout=5.0, mem_mb=512):
    """Return 1.0 if `code` followed by `tests` exits 0 within `timeout` seconds, else 0.0.

    NOT a security sandbox: no network or filesystem isolation. Use Docker/gVisor for untrusted code.
    """
    program = code + "\n\n" + tests + "\n"
    with tempfile.TemporaryDirectory() as tmp:
        path = os.path.join(tmp, "main.py")
        with open(path, "w") as f:
            f.write(program)
        try:
            proc = subprocess.run(
                [sys.executable, "-I", path], cwd=tmp, stdin=subprocess.DEVNULL,
                stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL, timeout=timeout,
                env={"PATH": os.environ.get("PATH", ""), "PYTHONHASHSEED": "0"},
                preexec_fn=_limits(int(timeout) + 1, mem_mb << 20),
            )
        except subprocess.TimeoutExpired:
            return 0.0
        return 1.0 if proc.returncode == 0 else 0.0


if __name__ == "__main__":
    tests = "assert add(2, 3) == 5"
    assert run_tests("def add(a, b):\n    return a + b", tests) == 1.0
    assert run_tests("def add(a, b):\n    return a * b", tests) == 0.0
    assert run_tests("while True:\n    pass", tests, timeout=1.0) == 0.0
    assert run_tests("def add(a, b:\n", tests) == 0.0  # syntax error
    print("ok: pass=1.0 fail=0.0 timeout=0.0 syntax-error=0.0")

Verified: ran locally, version seen: Python 3.9.6. Ran locally on Python 3.9 (macOS): passing example returns 1.0, failing 0.0, infinite loop 0.0 (timeout), syntax error 0.0. NOT a security sandbox: no network or filesystem isolation, and memory/process rlimits are applied only on Linux. Use inside a container (see docker-hardened-sandbox) for untrusted code.

5. Evaluation inside the training loop

  1. Baseline

    Run all four checks on the starting model. Save the outputs, the settings and the harness version.

  2. Small experiment

    Train on a small slice for a short run. Re-run the fast checks. If nothing moves, the problem is the data or the objective, not the scale.

  3. Compare per task

    Look at which tasks went from fail to pass and which went the other way. Gains that all come from one task family point to leakage or a narrow fix.

  4. Gate

    Before any larger run, require the held-out score to improve, regressions to stay within a threshold you set in advance, and a sample of passing outputs to look correct when read.

  5. Repeat with one change

    Change one thing at a time: the data, the filter, the learning rate. Record each run's settings and results in the experiment tracker.
