Stage 04

RL with verifiable rewards

Let the model try, run the tests, reward what passes. Environments, task sets, and verifiers.

Who needs this

For teams that can afford many rollouts and have a trustworthy verifier. It is the stage that most often moves hard-reasoning and agentic scores, and the stage where mistakes in the verifier become reward hacking.

Decisions you will make

  • Which task source: unit-tested function problems, competitive programming with test cases, repository issues with containerized tests, terminal tasks, SQL with execution match, or formal proofs checked by a proof assistant.
  • Which filter on difficulty. Tasks the model always solves or never solves give no learning signal, so keep a middle band of pass rates.
  • Which framework runs the rollouts and where the sandbox lives.

Pitfalls

  • Reward hacking: models edit or special-case tests, read hidden tests from disk, or use the network when it is on. Isolate the sandbox and keep tests out of reach.
  • Weak or sparse tests reward wrong code. Add test cases, or check them with a reference solution before using a task.
  • Run RL after the model already solves a fair share of tasks. From a weak start, most rollouts fail and the signal is thin.
