Stage 03

Preference and reward data

Teach what better means: pairs and judgments that rank code, ideally grounded in tests.

Who needs this

Useful when SFT has plateaued and you want a cheap alignment step before (or instead of) full RL. Pairs derived from test results are far more reliable than pairs judged by another model alone.

Decisions you will make

  • Execution-grounded pairs (passes tests versus fails tests) versus LLM-judged pairs. Prefer the first where you can get it.
  • Whether to train a reward model or skip it. For code, tests are often a better reward than a learned model, so verifiable-reward RL can replace this stage.
  • DPO versus other offline methods. Use the simplest one your trainer supports and compare on a held-out eval.

Pitfalls

  • LLM-judged preferences reward style and length. Control for length, or your model learns to write longer code.
  • Pairs where both samples pass (or both fail) carry little signal. Filter to pairs with a clear outcome gap.
  • Preference data built from a benchmark's tests can leak that benchmark into training.
