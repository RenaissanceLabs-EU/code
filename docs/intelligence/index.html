The idea underneath

Code and intelligence

What it means to compute, where computation stops, and what changes now that programs can be found by training instead of written by hand.

What it means to compute

In 1936, before any electronic computer existed, Alan Turing asked what it means to follow a rule mechanically. His answer was an imaginary machine: a strip of tape, a head that reads and writes one symbol at a time, and a finite table saying what to do next. In the same year Alonzo Church gave a completely different answer, a notation for functions called the lambda calculus. The two turned out to compute exactly the same things.

So has every reasonable definition proposed since. The claim that they always will, that anything computable by any mechanical procedure is computable by a Turing machine, is the Church-Turing thesis. It cannot be proved, because "mechanical procedure" is an informal idea, but nothing has contradicted it in ninety years.

Turing's paper contained a second idea that matters as much. One particular machine can read the description of any other machine from its tape and imitate it. This is the universal machine, and it is the theoretical basis of software. A computer does not have to be built for a task. It is built once, to run programs, and the task arrives later as data. Every level of the stack on this site is that idea applied again.

Simple rules are enough

A universal machine does not need to be complicated. Take a row of cells, each black or white. To get the next row, every cell looks at itself and its two neighbors and consults a table with eight entries. That table is the whole program. There are 256 possible tables, and one of them, called Rule 110, has been proved able to carry out any computation, given a suitable starting row of unlimited length.

The lesson reaches well beyond toy systems. Rich behavior does not require rich ingredients. A handful of gate types is enough to build a processor, a few dozen instructions are enough to run any software, and one arithmetic pattern repeated billions of times is enough for a language model. What code adds is organization, layer upon layer of it.

What cannot be computed

The same 1936 paper showed that computation has a hard edge. There is no program that can look at any program and its input and correctly say whether it will ever finish. This is the halting problem (the name came later; Turing's own paper proved an equivalent result), and it is impossible in principle, however clever the method or fast the machine.

In 1953 Henry Rice proved something broader. Every interesting question about what a program does, as opposed to how it is written, is undecidable in the same way. Does it ever print a 7? Does it compute the same function as this other program? Is it free of some bug? No program can answer any such question correctly for all programs.

This theorem is one reason for the shape of software engineering. Because no perfect checker can exist, every real checker gives something up. A type system refuses some correct programs. Tests examine a few inputs and stay silent on the rest. A proof settles the question completely, but a person or a model has to find the proof, and there is no guarantee one will be found. Programs and proofs are the same thing

There is an exact correspondence between logic and programming, noticed in pieces by Haskell Curry and William Howard. A type can be read as a proposition. A program of that type is a proof of the proposition. A function that turns any value of type A into a value of type B is a proof that A implies B, and running the program is the same as simplifying the proof.

This is not an analogy. Proof assistants such as Lean are programming languages in which the correspondence is used directly: to prove a theorem you write a program, and the type checker accepts it only if the proof is valid. It is why the proof form of a program sits at the top of the ladder, and why our map of mathematics and this map of code are two views of one subject. Mathematics is the part concerned with what is true. Code is the part that also has to run.

Programs that are found instead of written

For most of the history of computing, every program was written by a person who understood, at least locally, why each line was there. Machine learning breaks that link. Training is a search through an enormous space of possible programs, guided only by how well each candidate fits the examples. What comes out is a program in the strict sense, but one with no author and no explanation. The learned programs level of the stack lets you watch a very small one being found.

Such programs can do things nobody knows how to write by hand, including understanding language. They also give up the property that made software trustworthy: that someone could read it. A network's weights can be executed and tested. They cannot in general be reviewed or proved correct, though specific properties of small networks can be verified. Interpretability research is the effort to recover that ability.

Why it matters that models write code

When a model answers a question, you receive an answer, and you have to decide how far to trust it. When a model writes a program, you receive something of a different kind. The program can be read. It can be parsed, type-checked, run against tests, and in the best case proved. It can be kept, versioned and executed a billion times without the model being involved again.

Code is therefore the place where learned ability turns back into explicit, checkable structure. Everything on this site about the forms of a program is, from this angle, a description of the instruments available for inspecting what a model produces. That is the practical reason code is the best understood subject for training: the feedback is automatic and, when the checks are good, exact.

It also moves the bottleneck. Writing code was slow and checking it was slower. Models make writing fast. What limits the amount of trustworthy software is now verification: tests that cannot be gamed, specifications that say what is meant, and proofs where the stakes justify them. A society that runs on code will be shaped by how well that checking is done.

Structure that exists outside of minds

Writing let knowledge outlive the person who had it. Mathematics let reasoning be checked by someone else. Code added a third thing: knowledge that carries itself out. A program is a piece of understanding that has been made precise enough to act without the person who understood it, and to keep acting, unchanged, for as long as a machine will run it.

That is what makes code more than a tool for engineers. It is the medium in which a civilization stores procedures it can no longer afford to perform by hand, and now it is the medium in which artificial minds are built and in which they do much of their work. Understanding it, from the transistor to the trained model, is part of understanding how intelligence of any kind gets built and kept.

Landmarks: computation

  1. 1931
    Incompleteness Kurt Gödel

    Gödel's 1931 paper 'Über formal unentscheidbare Sätze der Principia Mathematica und verwandter Systeme I' showed that in any consistent formal system able to carry out a certain amount of elementary arithmetic some statements can be neither proved nor disproved, and that such a system cannot prove its own consistency. source

  2. 1936
    The Entscheidungsproblem is unsolvable Alonzo Church and Alan Turing

    Hilbert and Ackermann's 1928 book called the Entscheidungsproblem the main problem of mathematical logic, and in 1936 Church (a few months earlier) and Turing showed that no decision method exists for first-order logic, with Turing's paper introducing the Turing machine. source

  3. 1953
    Rice's theorem Henry Gordon Rice

    Rice's theorem says that all non-trivial semantic properties of programs are undecidable; it appears in Rice's 1953 paper 'Classes of Recursively Enumerable Sets and Their Decision Problems' (Transactions of the American Mathematical Society 74), though the theorem was proved in his 1951 doctoral dissertation. source

  4. 1964
    Algorithmic information Ray Solomonoff; Andrey Kolmogorov (1965); Gregory Chaitin (1966)

    Solomonoff gave a fuller account of the core theorem of algorithmic information in his 1964 'A Formal Theory of Inductive Inference' (first published in a 1960 report), Kolmogorov independently published it in Problems of Information Transmission in 1965, and Chaitin submitted his version to the Journal of the ACM in October 1966. source

  5. 1971
    NP-completeness Stephen Cook (1971), Richard Karp (1972), and independently Leonid Levin

    Cook's 1971 'The Complexity of Theorem-Proving Procedures' showed that satisfiability is NP-complete, and Karp's 1972 'Reducibility among Combinatorial Problems' showed that 21 combinatorial problems are NP-complete. source

  6. 2004
    Rule 110 is universal Matthew Cook

    Cook's 'Universality in Elementary Cellular Automata' (Complex Systems 15(1), 2004) argues that Rule 110, a one-dimensional elementary cellular automaton, is capable of universal computation, confirming a 1985 conjecture of Stephen Wolfram. source

  7. 2024
    BB(5) = 47,176,870 The bbchallenge collaboration

    The bbchallenge collaboration announced on July 2, 2024 that the fifth Busy Beaver value is S(5) = 47,176,870, with a proof checked in the Coq proof assistant that enumerates 181,385,789 five-state Turing machines and decides for each whether it halts (the paper appeared on arXiv in September 2025). source

Open problems: computation

  • P versus NP

    If it is easy to check that a solution to a problem is correct, is it also easy to solve the problem? Stephen Cook and Leonid Levin formulated the question independently in 1971, and it is one of the Clay Mathematics Institute's Millennium Problems. source

  • BB(6)

    As of November 2026 the bbchallenge front page highlights a six-state halting machine by mxdys (2025) showing that BB(6) is greater than 2↑↑↑5 in Knuth's up-arrow notation, so the true value is unknown and the team lists BB(6) as a new goal. source

  • The Collatz conjecture

    The Collatz conjecture asserts that repeatedly halving even numbers and sending odd N to 3N+1 reaches 1 from every positive integer, and Tao (2019) proved only that almost all orbits, in the sense of natural density, attain almost bounded values. source

Landmarks: code and intelligence

  1. 1950
    Computing Machinery and Intelligence Alan Turing

    Turing's October 1950 paper in Mind proposed to consider the question 'Can machines think?' and replaced it with the imitation game, in which a judge exchanging text with a human and a computer tries to tell which is the human. source

  2. 1955
    Dartmouth proposal John McCarthy, Marvin Minsky, Nathaniel Rochester, and Claude Shannon

    The August 31, 1955 'Proposal for the Dartmouth Summer Research Project on Artificial Intelligence' proceeded on the conjecture that every aspect of learning or any other feature of intelligence can in principle be so precisely described that a machine can be made to simulate it. source

  3. 2011
    Programming by example Sumit Gulwani, Microsoft Research

    Gulwani's POPL 2011 paper designed a string-manipulation language and an algorithm that synthesizes a program in it from input-output examples in a fraction of a second, for string-processing tasks that end users struggle with. source

  4. 2021
    Codex Mark Chen and colleagues, OpenAI

    Codex, a GPT language model fine-tuned on public GitHub code, solved 28.8% of the HumanEval problems on a single try (70.2% with 100 samples per problem), and a production version powers GitHub Copilot. source

  5. 2023
    Mechanistic reading of a learned algorithm Neel Nanda, Lawrence Chan, Tom Lieberum, Jess Smith, Jacob Steinhardt

    Nanda and colleagues fully reverse-engineered the algorithm that small transformers learn for modular addition, which uses discrete Fourier transforms and trigonometric identities to turn addition into rotation about a circle, explaining the 'grokking' behavior first reported by Power and colleagues in 2022. source

  6. 2023
    AlphaDev Daniel Mankowitz and colleagues, DeepMind

    AlphaDev, a deep reinforcement learning agent that treated finding a faster sorting routine as a single-player game, discovered small sorting algorithms that outperformed the previous human benchmarks and were integrated into the LLVM standard C++ library (Nature, June 2023). source

  7. 2025
    AlphaProof Thomas Hubert and colleagues, Google DeepMind

    AlphaProof (Nature, November 2025) learns formal proofs in Lean through reinforcement learning, and with AlphaGeometry 2 it reached a score equivalent to a silver medallist at the 2024 International Mathematical Olympiad, which the authors call the first medal-level performance by an AI system to their knowledge. source

Open problems: code and intelligence

  • Verifying learned programs

    Deep neural networks are hard to use in safety-critical systems because it is very difficult to give formal guarantees about their behavior, and Reluplex (CAV 2017) extended the simplex method to verify properties of networks with ReLU activations, evaluated on a prototype of a next-generation airborne collision avoidance system. source

  • Correct-by-construction code from models

    Without effective methods for ensuring that generated code is correct, LLM code generation could lead to undesirable outcomes, and Clover (2023) proposes consistency checks among code, docstrings, and formal annotations, evaluated on annotated Dafny programs. source

  • Specification versus intent

    Checking an implementation against a formal specification can be done mechanically, but there is no algorithmic way to ensure that the formal specification captures the user's intent, which is stated informally in natural language (Lahiri, 2024). source
