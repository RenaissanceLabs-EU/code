Change: a program is never finished

What is a program, if it is different every week?

Real programs are not written once. They are changed, daily, by many people, for decades. The unit of work in software is therefore the change and not the program: a small difference between two versions, with a reason attached, read by someone else before it is accepted, and recorded for good.

Version control systems such as Git keep every committed version, and the history stays unless someone rewrites it. That history is as much a part of the software as the current text, because it records why each line is the way it is.

It follows that most programming is reading. The job is to understand an existing system well enough to alter one part without breaking the rest. This is the hardest form for people and for models, because it needs every other form on this map at once, across thousands of files, together with knowledge that is written down nowhere: why it was built this way, and what its users have come to depend on.

Same behavior, different program

There are two classic ways to write Euclid's algorithm. The older one subtracts the smaller number from the larger until they are equal. The other takes a remainder, which does many subtractions in one step. On 48 and 18 both give 6. On 1,000,000 and 1 the first takes almost a million trips around its loop and the second takes one.

Replacing one with the other is a typical change: the behavior stays the same on the inputs it was meant for, the cost changes, and one behavior at the edges changes too (what happens when an input is zero). The figure below shows this change the way a programmer sees it.

What to notice
  • Version control stores and shows software in this form, and review happens on the diff, not on the whole file.
  • The diff is computed on text, one line at a time. Reindent a block and every line counts as changed, though nothing in the tree moved.
  • Both versions give the same answer here. Nothing in the diff tells you that. Someone, or something, had to run them.

Central ideas

Diff
The difference between two versions of a text, as lines removed and lines added.
Commit
One recorded change, with an author, a time and a message saying why.
Version control
A system that stores the full history of a project and lets many people change it at once.
Merge conflict
Two changes that touch the same lines, which the system cannot combine by itself.
Code review
Reading someone else's change before it is accepted.
Refactoring
Changing the structure of code without changing what it does.
Regression
Something that used to work and stopped working after a change.
Dependency
Code written by someone else that a program needs in order to run.

Landmarks

  1. 1975
    SCCS Marc Rochkind, Bell Labs

    Rochkind's 'The Source Code Control System' (IEEE Transactions on Software Engineering, December 1975) describes a tool for storing, updating, and retrieving all versions of modules and for recording who made each change, when, where, and why. source

  2. 1976
    diff James Hunt and Douglas McIlroy

    Hunt and McIlroy's Bell Laboratories Computing Science Technical Report 41, 'An Algorithm for Differential File Comparison' (1976; the scanned copy is dated July 1976 while other sources say June), describes diff, which reports differences between two files as a minimal list of line changes using a longest common subsequence algorithm. source

  3. 1985
    RCS Walter Tichy

    Tichy's 'RCS: A System for Version Control' (Software: Practice and Experience, July 1985) introduced the Revision Control System, which manages revisions of text documents, automates storing, retrieval, logging, and identification of revisions, and stores deltas between successive versions. source

  4. 2000
    Continuous integration Kent Beck (Extreme Programming, 1990s); Martin Fowler (article, September 2000)

    Kent Beck developed continuous integration as part of Extreme Programming in the 1990s, and Martin Fowler's article of September 10, 2000 (rewritten 2006 and 2024) describes it as each team member merging into a shared codebase at least daily with an automated build, including tests, verifying each integration. source

  5. 2005
    Git Linus Torvalds

    Linus Torvalds made the first commit of Git on April 7, 2005, titled 'Initial revision of "git", the information manager from hell'. source

Open problems and frontiers

  • What should a merge mean?

    Unstructured version control resolves merge conflicts by textual similarity and structured systems use language-specific knowledge, and Apel and colleagues (2011) proposed semistructured merge using annotated grammars, so a merge that is general across languages and still respects program structure is not settled. source

  • Understanding code someone else wrote

    Earlier studies say program comprehension takes up as much as half of a developer's time, and Xia and colleagues (2018) measured it with professionals across many applications, not only the IDE, because developers' comprehension activity goes well beyond the IDE. source

  • Supply chain attacks

    On March 29, 2024 Andres Freund reported that the upstream xz repository and the xz release tarballs 5.6.0 and 5.6.1 had been backdoored (CVE-2024-3094), with an obfuscated script in the tarballs that was not in the upstream git source, so verifying that the code people build is the code people reviewed is open. source

What this means for training models

This is the form that separates writing functions from doing software engineering. Benchmarks in the SWE-bench family give a model a real repository and a real issue, and judge its change by the project's own tests. Scores on them say more about practical use than any function-level benchmark, and they are also harder to build and easier to contaminate.

History is training data too. Most public commits are a before and an after, and many carry a stated reason, and reviews add a human judgment of the change. Agent trajectories record the reading, running and editing in between. The resources below cover commits, reviews, repository tasks and the environments that turn a repository into a place where a model can practice.
