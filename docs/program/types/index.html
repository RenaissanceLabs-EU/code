Types: what kind of thing is this?

What can be known about a program without running it?

A type says what kind of value something is: a whole number, a piece of text, a list of numbers, a function from numbers to yes-or-no. A type checker reads the tree and confirms that every operation is given the kind of value it needs. In a statically typed language you cannot add a number to true, and you cannot call something that is not a function. The checker establishes this for every possible run of the program at once, without running it a single time.

Languages differ in when they check. Statically typed languages such as C, Java, Rust and Haskell check before the program runs and refuse to build it if a type is wrong. Dynamically typed languages such as Python, JavaScript and Ruby check each operation at the moment it happens, so the same mistake appears only if and when that line is reached, possibly in front of a user.

Types are also where code first touches logic. In languages where every program is guaranteed to finish, a type can be read as a claim, and a program of that type as evidence for the claim. Followed far enough, that idea turns a type checker into a proof checker, which is the subject of the proof page.

There is a cost. A checker that never lets a bad program through must sometimes refuse a good one, and richer type systems ask the programmer to say more.

The same mistake in three languages

Passing true where a number belongs:

  • In the small language on this page, gcd(48, true) is rejected before it runs.
  • In Python, True counts as the number 1, so a gcd(48, True) written the same way runs and quietly returns True, which equals 1.
  • In JavaScript, "5" * 2 is 10 but "5" + 2 is the text "52".

None of these is an accident. Each is a decision a language made about what types are for.

What to notice
  • The working program contains no type annotations. Every type shown was inferred from use: b != 0 forces b to be a number, and a % b forces a to be one too.
  • Each mistake is found with its exact position, before any test exists.
  • "Forget a return" is a mistake about paths, not values: one route through the function gives nothing back.

Central ideas

Type
A classification of values that says which operations make sense on them.
Static checking
Checking types before the program runs, for all runs at once.
Dynamic checking
Checking each operation's types at the moment it executes.
Type inference
Working out types from how names are used, without the programmer writing them.
Soundness
The guarantee that a program accepted by the checker cannot hit a type error when it runs.
Generic type
A type with a blank to fill in, such as "list of T", so one piece of code serves many types.
Ownership
Rust's use of types to track who may read or change a piece of memory, catching a class of memory errors at compile time.

Landmarks

  1. 1908
    Theory of types Bertrand Russell

    Russell's 'Mathematical Logic as Based on the Theory of Types' (American Journal of Mathematics 30, 1908) presented type theory as a foundation for mathematics; the theory itself was first introduced in his 1903 Principles of Mathematics. source

  2. 1934
    Propositions as types Haskell Curry (1934); William Howard (manuscript 1969, published 1980)

    Curry observed in 1934 that the types of combinators can be read as axiom schemes of intuitionistic implicational logic, and Howard's 1969 manuscript, published only in 1980 as 'The formulae-as-types notion of construction', made explicit the analogy between simply typed lambda calculus and natural deduction. source

  3. 1940
    Simply typed lambda calculus Alonzo Church

    Church's 'A Formulation of the Simple Theory of Types' (Journal of Symbolic Logic 5, June 1940) introduced the simply typed lambda calculus as an attempt to avoid paradoxical uses of the untyped lambda calculus. source

  4. 1975
    Martin-Lof type theory Per Martin-Löf

    Martin-Löf's 'An Intuitionistic Theory of Types: Predicative Part' (presented at Logic Colloquium '73, published 1975) was the first of his type theories to be published and introduced identity types; the year is the publication year, and earlier versions circulated as preprints in 1971 and 1972. source

  5. 1978
    Principal types and polymorphic inference J. Roger Hindley (1969) and Robin Milner (1978)

    Hindley's 1969 paper on the principal type-scheme of an object in combinatory logic showed that the most general type can always be inferred, and Milner independently developed an equivalent method for his 1978 'A Theory of Type Polymorphism in Programming', first implemented in ML; the year given is Milner's paper. source

  6. 2018
    Ownership types in Rust Ralf Jung, Jacques-Henri Jourdan, Robbert Krebbers, Derek Dreyer (RustBelt); the Rust Core Team (1.0, May 15, 2015)

    Rust 1.0 shipped on May 15, 2015 with safety guarantees and no garbage collector or runtime, and RustBelt (POPL 2018, the year given) gave the first formal, machine-checked safety proof for a realistic subset of Rust and its ownership-based type system. source

Open problems and frontiers

  • Usable dependent types

    Dependent type theory, type checking, and unification are well understood, but Brady (2013) notes that combining them into a realistic, usable high-level language is folklore rediscovered by each implementor, and Idris is one attempt at a general-purpose dependently typed language. source

  • The cost of gradual typing

    Sound gradual typing inserts run-time checks at the boundary between typed and untyped code, and Takikawa and colleagues (POPL 2016) note that the few emerging implementations suffer performance overheads (a few report disastrous numbers) and propose a method to evaluate them, applied to Typed Racket. source

  • Types for concurrency and communication

    Behavioral types (interfaces, protocols, contracts, choreographies) aim to ensure correctness of communication-intensive systems, but Ancona and colleagues (2016) stress that applying them successfully requires settling pragmatic questions from how they are represented in a language to how they combine with methods and functions. source

What this means for training models

For a model, a type checker is a verifier one step stronger than a parser and nearly as cheap. It needs no tests, it covers all inputs, and its error messages say where and why. Systems that let a model compile, read the errors and try again lean on this constantly.

It also changes what is learnable. In a typed language a wrong guess is often caught at once. In a dynamic language the same guess runs and fails later or never, so the feedback is weaker. Open data for teaching types directly, such as type prediction for Python or TypeScript, exists but is small next to the data for writing functions.
