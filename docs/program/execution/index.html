Execution: the program runs

What does a program mean?

The meaning of a program is what happens when it runs. A machine takes the first instruction, carries it out, and moves to the next. Each step changes one small piece of state: a value on a stack, the contents of a variable, the position in the program. That is the model every programmer works with, and the hardware makes it look true, billions of times a second.

The semantics of a language is the exact rulebook for those steps. Under it, two programs that look nothing alike can mean the same thing, and two that differ by one character can mean entirely different things.

Here code parts ways with every other kind of writing. To learn what a program does in general, there is no method that always beats running it. In 1936 Alan Turing proved a result that comes to the same thing: no procedure can decide, for every program and input, whether the program will eventually stop. Execution is the ground truth. Types, tests and proofs are all ways of predicting or constraining what execution will do.

Euclid's algorithm, step by step

To find the greatest common divisor of 48 and 18, replace the pair by the smaller number and the remainder, and repeat until the remainder is zero:

trace
(48, 18)  ->  (18, 12)  ->  (12, 6)  ->  (6, 0)   answer: 6

Three trips around the loop. Each trip is thirteen instructions on the small machine used here, which you can follow one at a time below. The method is in Euclid's Elements, written around 300 BC, which makes it one of the oldest algorithms still run every day.

What to notice
  • The machine has no idea it is computing a greatest common divisor. It pushes, pops, compares and jumps.
  • When gcd is called, a new frame appears on the call stack with its own variables. When it returns, the frame is gone.
  • Change b != 0 to a != 0 and run. The machine does exactly what was written, straight into a division by zero.

Central ideas

State
Everything the machine holds at one moment: variables, stacks, and the position in the program.
Instruction
One step the machine can take, such as "push 0" or "jump to 13".
Call stack
The record of which functions are in progress, each with its own variables.
Semantics
The precise definition of what each construct of a language does when it runs.
Side effect
Anything a program does besides computing a value: printing, writing a file, sending a message.
Termination
Whether a program eventually stops. No general method can decide this for all programs.
Undefined behavior
A situation the language definition refuses to assign a meaning to. In C, reading past the end of an array is one.

Landmarks

  1. 1936
    Unsolvability of the Entscheidungsproblem (Church) Alonzo Church

    Church's 1936 'A Note on the Entscheidungsproblem' argued, without reference to computing machines, that the Entscheidungsproblem for first-order logic is unsolvable, a few months before Turing reached the same result. source

  2. 1936
    Turing machine Alan Turing

    Turing's 'On Computable Numbers, with an Application to the Entscheidungsproblem' (Proceedings of the London Mathematical Society, volume dated 1936-37) introduced the Turing machine and a universal machine that can interpret any other machine's description, and used them to show the Entscheidungsproblem unsolvable. source

  3. 1960
    Lisp and automatic storage reclamation John McCarthy, MIT

    McCarthy's April 1960 'Recursive Functions of Symbolic Expressions and Their Computation by Machine, Part I' defines LISP through recursive functions of symbolic expressions and describes automatic reclamation of unused list storage, a process he says he had already called garbage collection. source

  4. 1964
    Mechanical evaluation of expressions Peter Landin

    Landin's 'The Mechanical Evaluation of Expressions' (The Computer Journal, 1964) showed how forms of expression in programming languages can be modelled in Church's lambda notation and described a way of interpreting such expressions. source

  5. 1971
    Toward a mathematical semantics Dana Scott and Christopher Strachey, Oxford

    Scott and Strachey's report 'Toward a Mathematical Semantics for Computer Languages', issued by Oxford's Programming Research Group (library stamp October 1971), is an early report on the denotational approach to defining what programs mean. source

  6. 1981
    Structural operational semantics Gordon Plotkin, Aarhus University

    Plotkin's 1981 Aarhus report 'A Structural Approach to Operational Semantics' (DAIMI FN-19, reprinted with corrections in the Journal of Logic and Algebraic Programming in 2004) introduced structural operational semantics as a logical means to define operational semantics. source

Open problems and frontiers

  • A semantics for C as it is really used

    The ISO C standard leaves much unclear about pointers and memory objects, and Memarian and colleagues (2019) propose two coherent semantics for pointer provenance that try to reconcile the standard, mainstream compiler behavior, and existing C code, while describing ongoing interaction with the standards committee WG14. source

  • Concurrent memory models

    Shared-memory concurrency in C and C++ was long poorly defined, and Batty and colleagues (2011) found that the draft standards of the time harbored substantial problems in their details while giving a mathematical semantics for C++ concurrency. source

  • Predicting what a program will do

    Turing's 1936 paper showed that deciding whether a machine will ever print a given symbol is uncomputable, so no analysis can decide the behavior of every program, and abstract interpretation (Cousot and Cousot, 1977) instead describes computations in an abstract universe so that abstract execution gives some information about actual computations; getting useful, sound answers at acceptable cost is the ongoing question. source

What this means for training models

Most strong training signals for code come from this layer: run the candidate and see what happens. That is also why training on code needs sandboxes. A model's output is untrusted code, and it has to run somewhere it can do no harm.

Models themselves are weak at this layer. Predicting what a program prints, without running it, means carrying exact state through many steps, and benchmarks built to test that skill show models losing track well before a real machine would. Execution traces are one answer: train on what programs actually did. The larger answer is to let the model run the code and read the result, which turns a writer into an agent.
