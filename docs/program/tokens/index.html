Tokens: the words of a language

Where does one word of a program end and the next begin?

Before a program can be understood, its text is cut into tokens: the smallest pieces that mean something on their own. In while b != 0 there are four: while, b, != and 0. The cutting is called lexing. Its rules are simple enough to write as patterns, and it is the first thing most compilers and interpreters do.

Tokens come in a few kinds: keywords the language reserves, names the programmer invents, numbers, operators and punctuation. Spaces and comments are thrown away once they have done their job of keeping words apart, which is why most languages let you lay code out however you like.

The word has a second meaning that matters on this site. Language models also cut text into tokens, but theirs are learned from statistics instead of defined by a grammar. A model's tokenizer may split one name into three pieces or glue a bracket to the line break after it. So the same program is tokenized twice, by two unrelated rules: once for the machine that will run it, and once for the model that reads or writes it.

Longest match wins

A lexer reads left to right and always takes the longest piece that fits. That one rule settles questions that would otherwise be ambiguous:

  • a<=b is three tokens (a, <=, b), not four. The lexer prefers <= to < followed by =.
  • a = b % 2 and a=b%2 are the same five tokens. The spaces only separate.
  • while b is two tokens. whileb is one: a name the programmer made up.
What to notice
  • Delete every space you can. As long as two words do not merge, the tokens stay the same.
  • The comment shows up as a token here and is dropped before the next stage. To the machine it was never part of the program.
  • Type a character the language does not have, such as @. This is the earliest possible error: the text cannot even be cut into words.

Central ideas

Token
The smallest meaningful piece of program text, with a kind (keyword, name, number, operator) and a position.
Lexer
The part of a compiler that turns characters into tokens. Also called a scanner.
Keyword
A word the language reserves for itself, such as while or return.
Identifier
A name chosen by the programmer for a variable, function or type.
Literal
A value written out directly, such as 42 or "hello".
Longest match
The rule that a lexer takes the longest token that fits at each position.
Subword token
A piece of text in a language model's learned vocabulary. It need not line up with the language's own tokens.

Landmarks

  1. 1975
    Lex Mike Lesk and Eric Schmidt, Bell Laboratories

    Lesk and Schmidt's 'Lex - A Lexical Analyzer Generator' (Bell Laboratories, 1975; Lesk's Computing Science Technical Report 39 is dated October 1975 and the Unix manual version July 21, 1975) described a program that generates lexical analyzers. source

  2. 1994
    Byte pair encoding Philip Gage

    Philip Gage described byte pair encoding in 1994 as a data compression method in 'A New Algorithm for Data Compression' (The C Users Journal), the algorithm later reused to build subword vocabularies. source

  3. 2016
    Subword units for neural models Rico Sennrich, Barry Haddow, and Alexandra Birch

    Sennrich, Haddow, and Birch proposed segmenting rare words into subword units with the byte pair encoding algorithm for neural machine translation, reporting BLEU gains on WMT 15 English-German and English-Russian (posted to arXiv in August 2015, published at ACL 2016, which is the year given). source

  4. 2018
    SentencePiece Taku Kudo and John Richardson

    SentencePiece (EMNLP 2018 demo) is an open-source subword tokenizer and detokenizer that trains directly on raw text, without requiring pre-tokenized words, which makes the whole text-to-tokens pipeline language independent. source

  5. 2021
    Token-free byte models Linting Xue and colleagues, Google

    ByT5 showed that a standard Transformer with minimal changes can process raw bytes, with byte-level models competitive with token-level ones, more robust to noise, and better at spelling and pronunciation tasks. source

Open problems and frontiers

  • Tokenizing numbers

    Popular models split numbers differently (LLaMa and PaLM use single digits, GPT-3.5 and GPT-4 use separate tokens for 1-, 2-, and 3-digit numbers), and Singh and Strouse (2024) study how this choice affects arithmetic in frontier models. source

  • Tokens the model never learned

    Because tokenizer creation is disconnected from model training, vocabularies can contain tokens nearly absent from training data (the SolidGoldMagikarp case) that induce unwanted behavior, and Land and Bartolo (2024) note that a reliable way to detect them had been missing. source

  • Can bytes replace tokens at scale?

    The Byte Latent Transformer (December 2024) groups bytes into patches by next-byte entropy and reports a FLOP-controlled scaling study up to 8B parameters and 4T training bytes, so whether tokenizer-free models can fully replace tokenizers at frontier scale is not yet shown. source

What this means for training models

Pretraining a language model on code is next-token prediction: given the tokens so far, guess the next one. Completion in an editor is the same task used directly, and fill-in-the-middle is its variant with text on both sides of the gap.

Two consequences follow. First, everything a model reads or writes is measured in its own tokens, so a large repository does not fit in view at once, and what to show the model becomes a problem of its own. Second, the model's tokens ignore the language's structure. Indentation, long identifiers and rare symbols can each cost many tokens, and the same code formatted differently is a different input. Careful pipelines normalize formatting and place fill-in-the-middle gaps on real token or syntax boundaries instead of at random characters.
