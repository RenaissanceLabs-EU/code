Proof: correct for every input

Can a program be known correct for inputs nobody has tried?

A proof shows that a program meets its specification for every input, by reasoning instead of trying. A proof assistant such as Lean, Rocq or Isabelle checks each step of the reasoning mechanically, so the trust rests on a small checking program and not on a reader's attention.

This is where code and mathematics become the same activity. Under the Curry-Howard correspondence, in a language where every program terminates, a proposition is a type and a proof of it is a program of that type. In Lean and Rocq, checking a proof is type checking. Real systems have been verified with proof assistants, among them the seL4 microkernel (in Isabelle/HOL) and the CompCert C compiler (in Coq, now Rocq), under stated assumptions about what lies outside the proof.

The cost is labor. Writing the proof usually takes far more effort than writing the program. And a proof is only as good as its specification. It establishes that the program does what the statement says. Whether the statement says what you wanted is a question no checker answers.

Euclid's algorithm, proved in Lean

The definition, a proof that it always terminates, and a theorem that its result divides both inputs, as accepted by Lean 4:

Lean 4
def gcd : Nat → Nat → Nat
  | a, 0 => a
  | a, b + 1 => gcd (b + 1) (a % (b + 1))
termination_by _ b => b
decreasing_by exact Nat.mod_lt _ (Nat.succ_pos _)

theorem gcd_dvd (a b : Nat) : gcd a b ∣ a ∧ gcd a b ∣ b := by
  induction b using Nat.strongRecOn generalizing a with
  | _ b ih =>
    cases b with
    | zero => simp [gcd]
    | succ n =>
      rw [gcd]
      have h := ih (a % (n + 1)) (Nat.mod_lt _ (Nat.succ_pos _)) (n + 1)
      exact ⟨(Nat.dvd_mod_iff h.1).mp h.2, h.1⟩

The theorem covers all pairs of natural numbers, of which there are infinitely many. Look at what it does not say, though: that the result is the greatest common divisor. A function that always returned 1 would satisfy this statement too. Saying completely what you mean is the hard part of verification.

What to notice
  • Each square is one pair of numbers, checked by brute force against the definition of greatest common divisor.
  • Doubling the range makes four times the work, and the unchecked region is still infinite.
  • The pattern of colored squares is a theorem of its own: the share of pairs with no common factor tends to 6/π².

Central ideas

Specification
A precise statement of what a program is supposed to do.
Invariant
Something that stays true every time around a loop. For Euclid: the common divisors of the pair never change.
Proof assistant
A program that checks proofs step by step and accepts nothing it cannot verify.
Trusted kernel
The small core of a proof assistant that does the checking. Only it has to be right, apart from the axioms and the system it runs on.
Termination proof
An argument that a program always stops, usually by showing some quantity shrinks at every step.
Hoare triple
A claim of the form: if this holds before the code runs and the code finishes, that holds after.
Propositions as types
The reading of types as claims and programs as their proofs.

Landmarks

  1. 1969
    Axiomatic basis for programs C. A. R. Hoare (following Robert Floyd, 1967)

    Hoare's 'An Axiomatic Basis for Computer Programming' (Communications of the ACM, October 1969) set out axioms and rules of inference for proving properties of computer programs, following Floyd's 1967 'Assigning Meanings to Programs'. source

  2. 1972
    LCF proof checker Robin Milner

    Milner's May 1972 Stanford memo AIM-169, 'Logic for Computable Functions: description of a machine implementation', describes LCF, a proof-checker for a logic of computable functions. source

  3. 1975
    Guarded commands and a calculus for deriving programs Edsger W. Dijkstra

    Dijkstra's 'Guarded Commands, Nondeterminacy and Formal Derivation of Programs' (Communications of the ACM, August 1975) introduced guarded commands as a building block for alternative and repetitive constructs and showed a calculus for the formal derivation of programs expressed in them. source

  4. 2005
    Four color theorem checked in Coq Georges Gonthier (with Benjamin Werner), Microsoft Research and INRIA

    Gonthier's report describes a formalization of the Four Colour Theorem proof fully checked by Coq v7.3.1, completed in 2005, in which only the statement of the theorem needs review while the rest (99.8% per the abstract) is self-checking. source

  5. 2009
    CompCert Xavier Leroy, Inria

    Leroy's 2006 POPL paper certified in Coq a compiler from Cminor to PowerPC assembly, and his 2009 'Formal Verification of a Realistic Compiler' reports CompCert, a Coq-verified compiler (proof of semantic preservation) from Clight, a large subset of C, to PowerPC assembly; the year given is the 2009 paper. source

  6. 2009
    seL4 Gerwin Klein and colleagues, NICTA and UNSW

    The seL4 SOSP 2009 paper reports the formal, machine-checked verification of the seL4 microkernel from an abstract specification down to its C implementation, which the authors say is, to their knowledge, the first formal proof of functional correctness of a complete, general-purpose operating-system kernel. source

  7. 2013
    Lean and Mathlib Leonardo de Moura (Lean); the mathlib community

    Lean's first commit was in July 2013 by its creator Leonardo de Moura, Lean 4.0 was officially released in September 2023, and mathlib is a community-driven library of mathematics formalized in Lean with dependently typed foundations. source

Open problems and frontiers

  • Proof automation by learning

    AlphaProof (Nature 2025) learns to find formal proofs in Lean by reinforcement learning on millions of auto-formalized problems and, with AlphaGeometry 2, reached a score equivalent to a silver medallist at the 2024 International Mathematical Olympiad using multi-day computation, so cheap, general automation for large proofs and software is not yet here. source

  • Is the specification right?

    Fonseca and colleagues (EuroSys 2017) found 16 bugs in three formally verified distributed systems (IronFleet, Verdi, Chapar), some invalidating the verification guarantees, caused by violated assumptions, which shows that a proof is only as good as its specification and trusted base. source

  • The cost of verified software

    Staples and colleagues (2014) studied nine projects associated with L4.verified, the seL4 verification, and found strong linear relationships between effort and proof size, so the human effort of proof grows with the size of what is proved. source

What this means for training models

A proof checker is the strongest verifier there is. A program that only works on the examples cannot satisfy it, so it closes the loophole tests leave open, though not every loophole: unfinished-proof placeholders, added axioms and weak statements can still be gamed. That makes proof a natural target for training by reward: the model edits a proof, the kernel says yes or no, and no judge is needed.

Models that write Lean proofs have improved quickly, and our sister site maps mathematics with Lean environments built for this. Verified code generation, where a model writes a program together with a proof that it meets a specification in a language such as Dafny or Verus, is younger and smaller. The open question is whether the specification can be trusted, since that is the one part a checker takes on faith.
