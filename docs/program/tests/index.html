Tests: checking behavior by example

How do you know a program is right?

A test runs a program on a chosen input and compares the result with what was expected. It is the everyday way of knowing that software works: cheap, automatic and concrete. Large projects run thousands of tests on every change.

The weakness is just as concrete. A test checks the inputs someone thought of. A program with infinitely many possible inputs passes its tests after being tried on a few of them. Tests can show that a bug is present. Unless every possible input can be tried, they cannot show that none remain.

For training models, tests are what make code special among the things a model can learn. An answer can be checked by a machine, with no person judging it. A test suite's pass or fail is a reward, and nearly all reinforcement learning for code rests on it. It inherits the weakness exactly: the program that passes the tests is not necessarily the program anyone wanted.

A wrong program that passes

Suppose the tests for gcd are five examples. Here is a program that passes every one:

the small language used on this site
fn gcd(a, b) {
  if a == 48 { return 6 }
  if a == 17 { return 1 }
  if a == 0 { return 9 }
  if a == 12 { return 12 }
  return 25
}

It contains no idea of what a divisor is. It has memorized the answer sheet. A person would be embarrassed to write it, but an optimizer that is rewarded only for passing tests has no such feeling, and will find programs like it.

What to notice
  • "Off by one" passes four of the five visible tests. A small suite can miss a bug that only shows on some inputs.
  • "Wrong operator" never finishes on most inputs. The harness has to give up after a step limit, because no test can wait forever.
  • "Memorize the visible tests" scores five out of five, then zero out of five on inputs it has not seen. Held-out tests are the standard defense.

Central ideas

Unit test
A small test of one function or component on one input.
Oracle
The thing that knows the right answer for a test: an expected value, a reference program, or a property.
Coverage
The share of a program's lines or branches that the tests cause to run.
Property-based test
A test that states a rule (the result divides both inputs) and tries many generated inputs against it.
Fuzzing
Feeding a program huge numbers of random or mutated inputs to find crashes.
Regression test
A test added after a bug is fixed, so the same bug cannot return unnoticed.
Held-out test
A test hidden from whoever, or whatever, writes the program.

Landmarks

  1. 1947
    The Harvard Mark II moth Harvard Mark II team (Grace Hopper was in the lab but the Smithsonian says the logbook was probably not hers)

    On September 9, 1947 a moth found stuck in the Harvard Mark II's switches was taped into its logbook with the note 'First actual case of bug being found', but 'bug' for a fault was already older (an 1878 Edison letter, an 1889 Pall Mall Gazette report), and the Smithsonian says the logbook was probably not Hopper's. source

  2. 1972
    Testing shows the presence of bugs Edsger W. Dijkstra

    In 'The Humble Programmer' (ACM Turing Lecture, 1972, EWD 340) Dijkstra wrote that program testing can be a very effective way to show the presence of bugs but is hopelessly inadequate for showing their absence. source

  3. 1978
    Coupling effect and mutation testing Richard DeMillo, Richard Lipton, and Frederick Sayward

    'Hints on Test Data Selection: Help for the Practicing Programmer' (Computer, April 1978) states the coupling effect, that tests which uncover simple errors are also effective in uncovering much more complex ones, the premise behind mutation testing. source

  4. 1990
    Fuzz testing Barton Miller, Lars Fredriksen, and Bryan So

    'An Empirical Study of the Reliability of UNIX Utilities' (Communications of the ACM, December 1990) built a random-character 'fuzz' generator, fed it to UNIX utilities, and classified the program bugs that caused the crashes. source

  5. 1997
    JUnit and the xUnit family Kent Beck and Erich Gamma

    According to Martin Fowler, Beck and Gamma created JUnit in 1997, pair programming the first version test-first on a flight from Zurich to the OOPSLA conference in Atlanta, spreading the framework style that began with Beck's Smalltalk testing framework. source

  6. 2000
    QuickCheck Koen Claessen and John Hughes

    QuickCheck (ICFP 2000) lets a Haskell programmer state properties of programs as Haskell functions and test them automatically on random input, with custom test data generators. source

  7. 2013
    American fuzzy lop Michal Zalewski (lcamtuf)

    American fuzzy lop, first publicly released as version 0.21b on November 12, 2013, uses compile-time instrumentation and genetic algorithms to find test cases that trigger new internal states in the targeted binary, and it is described by its author as a security-oriented fuzzer. source

Open problems and frontiers

  • The test oracle problem

    Given an input, distinguishing the corresponding correct behavior from incorrect behavior is called the test oracle problem, and Barr and colleagues' 2015 survey says that when modelling, specifications, contracts, and metamorphic testing are not adequate, the final source of oracle information remains the human. source

  • Flaky tests

    Regression testing assumes that an unmodified test always passes or always fails for the same code, but flaky tests have non-deterministic outcomes, and Luo and colleagues (2014) studied 201 commits that likely fix flaky tests in 51 open-source projects to classify the root causes. source

  • Judging how good a test suite is

    Code coverage is often used as a proxy for a test suite's ability to detect faults, but earlier studies reached no consensus on how strong the relationship is, and Inozemtseva and Holmes (2014) titled their result 'Coverage is not strongly correlated with test suite effectiveness'. source

What this means for training models

In training, the test suite is the teacher. A model writes a program, the tests run, and the score becomes the reward. The quality of that reward is the quality of the tests. Thin suites accept wrong programs, and several well-known benchmarks were extended by other researchers with many more tests per problem once this was measured: HumanEval+ and MBPP+ have about 80 and 35 times as many tests as the originals.

Models also exploit tests when they can. If the tests are readable from inside the sandbox, a model can special-case them, edit them, or read the expected values. Sound setups keep tests out of reach, hold some back, and review a sample of passing solutions by hand. The guide and pitfalls pages cover this in practice.
