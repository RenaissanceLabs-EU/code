Text: a program begins as a file of characters

If a program is only a file of characters, what makes it different from a letter?

A program starts life as plain text: a sequence of characters, stored as a sequence of bytes. Nothing in the file marks it as special. The same bytes can be opened in an editor, printed, or sent in an email. What makes them code is that another program can read them and act on what they say.

Plain text is an old and deliberate choice. It means every tool ever made for text also works on programs: editors, search, comparison, version control, and now language models, which read code the same way they read prose. The price is that text carries no structure of its own. Where a statement ends, which name belongs to which function, what any of it means: all of that has to be worked out from a flat line of characters. The other seven forms on this map are that working out.

One line, three ways of looking

The line a = b % 2 is nine characters. Stored on disk it is nine numbers, here in hexadecimal:

bytes, in hexadecimal
61 20 3D 20 62 20 25 20 32

The letter a is 61, the space is 20, and the percent sign is 25. These values were fixed by the ASCII standard in the 1960s and have not changed since for these characters. Add a character from outside that old set, such as é, and it takes two bytes (C3 A9) under UTF-8, the encoding most source code uses today.

What to notice
  • In most languages the keywords, digits and operators take one byte each, exactly as in ASCII. Strings, comments and a few languages (Lean uses → and ∧) reach for characters outside it. UTF-8 was designed so that an old ASCII file is already a valid UTF-8 file.
  • A space is a byte like any other (20). A tab is a different byte (09). Two programs can look the same on screen and differ on disk, which matters in languages such as Python where indentation is part of the meaning.
  • A typical emoji takes four bytes, and ones built from several parts take many more. The machine does not know it is a face. It does not know a is a letter either.

Central ideas

Character
One written symbol: a letter, a digit, a bracket, a space.
Code point
The number Unicode assigns to a character. a is U+0061.
Encoding
The rule that turns code points into bytes. UTF-8 uses one to four bytes per character.
Byte
Eight bits, a number from 0 to 255. The unit in which files are stored and sent.
Source file
A text file holding part of a program. Large programs have thousands.
Line ending
The invisible character that ends a line: one byte (0A) on Unix systems, two (0D 0A) on Windows.

Landmarks

  1. 1963
    ASCII American Standards Association, X3.2 subcommittee (work began with a 1961 proposal by IBM engineer Bob Bemer)

    The American Standards Association published ASA X3.4-1963, the first edition of ASCII, after work that began in May 1961 with a proposal by Bob Bemer; a major revision followed as USAS X3.4-1967. source

  2. 1984
    Literate programming Donald Knuth

    Knuth's 'Literate Programming' (The Computer Journal 27(2), 1984) presented WEB, a combined programming language and documentation system, and argued for treating a program as a piece of literature addressed to human beings rather than to a computer. source

  3. 1991
    Unicode 1.0 Unicode Consortium

    Volume 1 of The Unicode Standard, Version 1.0 was first printed in October 1991 (Volume 2 followed in June 1992), starting the character repertoire that UTF-8 later encoded. source

  4. 1992
    UTF-8 Ken Thompson, with design criteria from Rob Pike (Plan 9, Bell Labs)

    Ken Thompson devised UTF-8 in September 1992 following Rob Pike's design criteria, so that Plan 9, the first system to run it, could use Unicode without disrupting ASCII, whose byte values never appear inside longer UTF-8 sequences. source

  5. 2003
    UTF-8 becomes an Internet Standard F. Yergeau (RFC 3629, STD 63)

    RFC 3629 (November 2003) made UTF-8 an Internet Standard and requires decoders to reject overlong forms such as C0 80 for U+0000, a loophole used in a widespread 2001 attack on web servers. source

Open problems and frontiers

  • Invisible and look-alike characters in source code

    Trojan Source (Boucher and Anderson, first posted October 2021, USENIX Security 2023) showed that bidirectional Unicode control characters make source display in a different order than compilers read it, with working attacks in twelve languages (CVE-2021-42574, and CVE-2021-42694 for the homoglyph variant). Unicode's UTS #39 offers confusable detection but says its skeleton is for testing confusability only, not for normalizing identifiers, so how every language, editor, and review tool should treat such characters is still unsettled. source

  • Line endings and encodings do not round-trip cleanly

    Git has to convert line endings between LF and CRLF and re-encode files such as UTF-16 to UTF-8 on commit, and its own documentation warns that conversions may be irreversible and that non-UTF re-encoding may not be round-trip safe. source

  • When are two identifiers the same name?

    UAX #31 recommends Normalization Form C for identifiers in case-sensitive languages and NFKC in case-insensitive ones, but these are recommended defaults, so whether and how each language normalizes identifiers is left to the language. source

What this means for training models

A language model meets code mostly at this layer. Its training data is source text, and its output is source text. Every structure described on the following pages is something the model has to infer from characters, because it is rarely handed the tree or the types.

So the data work at this layer decides a great deal. Public code is full of exact and near-exact copies, files produced by tools instead of people, minified bundles, and secrets that were committed by mistake. Each file also carries its own license. Collecting code as text, removing duplicates, filtering what should not be learned from, and keeping the license of every file are the first steps of any training run, and the resources below are the corpora and tools for them.
