Networks and distributed systems: programs that talk

How do computers that cannot trust the wire, or each other, act as one system?

Almost no program runs alone. It asks other programs on other machines for data, time, names and payments, over networks that can lose, delay, reorder and duplicate anything sent.

What holds this together is the protocol: a precise, published agreement about what bytes mean when they travel between machines. The internet is a stack of them. IP moves a packet toward an address. TCP turns unreliable packets into a reliable stream. DNS turns names into addresses. TLS encrypts. HTTP asks for a page. Each protocol solves one problem and treats everything above it as cargo, so a layer can be replaced with little change to the others, though not none.

Systems spread over many machines face problems a single machine does not have. There is no shared clock, machines fail partway, sometimes many at once, without warning, and a silent machine is indistinguishable from a slow one. Things one computer gets for free, such as a single order of events or a single version of the truth, have to be constructed with algorithms for agreement, and some combinations of guarantees are provably impossible.

At this scale the arrangement of machines is also written down as code. Infrastructure-as-code tools describe servers, networks and permissions in text files, so that a data center can be reviewed, versioned and rebuilt like a program.

What happens when you open a web page

Typing an address and pressing Enter usually sets off four conversations, each in its own protocol (with HTTP/3, QUIC does the TCP and TLS steps together):

  • DNS: ask which numeric address the name belongs to.
  • TCP: open a connection to that address and agree on how to number the bytes.
  • TLS: prove the server is who it claims to be, and agree on encryption keys.
  • HTTP: ask for the page, and receive it.

Each of these travels as packets. Each packet carries the layers nested inside one another, as the figure shows.

What to notice
  • A one-byte message still costs 58 bytes of headers and trailer, and Ethernet pads a frame that small up to 64 bytes. A large file pays about 4%.
  • On a standard 1,500-byte link, past 1,460 bytes the data no longer fits in one packet and is split. The receiving end reassembles it, and asks again for any piece that went missing.
  • Routers along the way forward using only the IP layer. They neither know nor care that the cargo is a web page.

Central ideas

Protocol
A published agreement on the format and order of messages between machines.
Packet
A small block of data with a header saying where it is from and where it is going.
Encapsulation
Wrapping one protocol's message inside another's, layer by layer.
Address and name
Machines are found by number (IP address). People use names, which DNS translates.
Reliability
Getting correct, ordered delivery out of a network that promises neither, by numbering, acknowledging and resending.
Consensus
Getting several machines to agree on one value even though some may fail. Paxos and Raft are the standard algorithms.
Replication
Keeping copies of the same data on several machines, and keeping them consistent.
Infrastructure as code
Describing machines, networks and their settings in text files that tools turn into running systems.

Landmarks

  1. 1964
    Distributed communications Paul Baran, RAND

    RAND memorandum RM-3420 (1964) proposed an all-digital network of standardized message blocks with store-and-forward routing and no central control point, designed to survive damage to nodes and links. source

  2. 1969
    First ARPANET message Leonard Kleinrock's UCLA group and SRI

    At 10:30 p.m. on October 29, 1969 the first ARPANET message was sent from UCLA's Boelter Hall to the Stanford Research Institute, the first packet-switching network of its kind, which also introduced protocol layering. source

  3. 1973
    Ethernet Robert Metcalfe and David Boggs, Xerox PARC

    Ethernet was invented at Xerox PARC in 1973, inspired by ALOHAnet, and a 1980 Xerox, DEC and Intel specification became IEEE 802.3, the local network standard. source

  4. 1974
    Transmission Control Program Vinton Cerf, Yogen Dalal and Carl Sunshine

    RFC 675 (December 1974) specified the Internet Transmission Control Program, with processes exchanging letters that may be split into fragments across packet networks, the ancestor of TCP (the Cerf and Kahn paper was also published in 1974). source

  5. 1978
    Time, Clocks, and the Ordering of Events Leslie Lamport

    The CACM paper of July 1978 (his most cited, per Lamport) introduced the ordering of events in a distributed system. source

  6. 1983
    Domain Name System Paul Mockapetris

    RFC 882 (November 1983) introduced domain-style names and the servers and protocols to resolve them, (it was obsoleted by RFC 1034 and 1035). source

  7. 2018
    TLS 1.3 Eric Rescorla, IETF

    RFC 8446 (August 2018) specified TLS 1.3, designed to prevent eavesdropping, tampering and message forgery, and obsoleted RFC 5246 (the page now marks 8446 itself as superseded by RFC 9846). source

Open problems and frontiers

  • Post-quantum migration

    On August 13, 2024 NIST announced approval of FIPS 203 (ML-KEM, from CRYSTALS-Kyber), FIPS 204 (from Dilithium) and FIPS 205 (from SPHINCS+) to resist future quantum attacks; migrating deployed protocols and keys is open. source

  • Securing internet routing

    RFC 6480 (2012) describes RPKI, which lets address holders verifiably authorize ASes to originate routes, because BGP assumes the originating AS is authorized; securing routing across independent operators end to end is open. source

  • Verified distributed systems

    IronFleet (SOSP 2015) proved safety and liveness for a Paxos-based replicated state machine library and a sharded key-value store with competitive performance; verifying production-scale systems is open. source

What this means for training models

This level is thin in open training data. Code that configures infrastructure is hard to check without the infrastructure: a correct answer creates real machines, which is slow and costs money. Benchmarks here either compare a model's configuration with a reference, check it with a policy tool, or run it against a simulated cloud.

Protocol and distributed-systems reasoning is thinner still. The bugs depend on timing and failure, which unit tests do not exercise. The methods that do find them, model checking and randomized fault injection, have, to our knowledge, not yet been turned into training environments at scale.
