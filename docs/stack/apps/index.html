Applications and data: the programs people use

What is all this machinery for?

An application is where code meets a human need: a browser, a payroll system, a game, a medical record, a spreadsheet. Much of the world's code lives at this level, and most of it is ordinary. It is forms, records, reports and the rules of some organization, written down exactly.

Structurally, an application is state plus rules for changing it. The state has to outlive the program, so it goes in a database. The relational model, proposed by Edgar Codd in 1970, treats data as tables. SQL, developed a few years later, lets questions be asked in a declarative language: you say what you want and the database works out how to fetch it. Transactions guarantee that a change happens completely or not at all, which is why a transfer between two bank accounts cannot lose money halfway.

Above the state sits the interface. The web browser turned into a universal one: a program on any server can show itself on any screen through three languages, HTML for structure, CSS for appearance and JavaScript for behavior.

Not all programming here looks like programming. A spreadsheet formula is a program, and for many people it is the first one they ever write.

Saying what, not how

A question to a database, in SQL:

SQL
SELECT item, price * count AS total
FROM orders
WHERE price > 3
ORDER BY total DESC;

Nothing here says how to find the rows, in what order to read the disk, or which index to use. The same query runs unchanged on ten rows or ten billion, and the database chooses a different plan for each. This is declarative code: a description of the result, with the procedure left to the system.

What to notice
  • You never say in which order to compute. Each formula names what it depends on, and the sheet derives the order.
  • Make D2 refer to D5 and the sheet reports a loop: a definition that depends on itself has no value.
  • This is the same idea as the SQL query above. State what each thing is, and let the system work out how.

Central ideas

State
The data an application has to remember: accounts, documents, orders.
Database
A program whose job is to store state safely and answer questions about it.
Transaction
A group of changes that takes effect completely or not at all.
Declarative code
Code that describes the result wanted and leaves the method to the system.
Client and server
The split between the program a person touches and the program that holds the shared state.
User interface
The part of a program a person sees and acts on.
Framework
A large reusable skeleton that an application fills in, instead of starting from nothing.
API
The set of requests one program agrees to answer for others.

Landmarks

  1. 1970
    Relational model of data Edgar F. Codd, IBM San Jose Research Lab

    Codd's 1970 paper proposed organizing information as linkable tables so users can query without knowing the physical layout, with relationships based on data values, and IBM's System R project (1973) tested the idea, with SQL developed concurrently. source

  2. 1972
    Xerox Alto Chuck Thacker (hardware), Butler Lampson (software), Xerox PARC

    The Alto project began in 1972 (Lampson dates the system software start to mid-1973) and pioneered raster displays, the mouse, windows, menus, Ethernet and the first WYSIWYG editor. source

  3. 1979
    VisiCalc Dan Bricklin and Bob Frankston, Software Arts

    The first spreadsheet for personal computers, released in 1979 for the Apple II (prototyped in spring 1978), became the killer application that drove Apple II sales. source

  4. 1989
    World Wide Web Tim Berners-Lee, CERN

    Berners-Lee wrote the first proposal in March 1989, had a first server and browser running by the end of 1990, announced the software in August 1991, and CERN released the source on a royalty-free basis on April 30, 1993. source

  5. 2000
    SQLite The SQLite project

    The project started in May 2000 (the project page's own two links give 2000-05-09 and 2000-05-29) as a serverless, self-contained transactional SQL engine in one file, and its authors call it the most widely deployed database in the world. source

Open problems and frontiers

  • Reliability at planetary scale

    A faulty content update from CrowdStrike in July 2024 disrupted about 8.5 million Windows devices by Microsoft's estimate, showing that one defect in widely deployed software can fail systems worldwide; engineering updates that fail safely is open. source

  • Accessibility of the web

    WebAIM's 2026 analysis of one million home pages found detectable WCAG 2 failures on 95.9 percent of them, up from 94.8 percent in 2025, with low-contrast text on 83.9 percent; making accessible output the default is open. source

What this means for training models

Most benchmark tasks that involve a whole repository are application code: web frameworks, data libraries, command-line tools. Their tests come with the project, which is what makes them usable as verifiers.

SQL has its own line of work. A model translates a question into a query, and the check is whether the query returns the same rows as a reference query on a real database. Interface code is harder to verify, because "looks right" is not a test, so those benchmarks compare screenshots or drive the page with a script. Data analysis tasks sit between the two: there is an answer to check, but many correct routes to it.
