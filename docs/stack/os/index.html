Operating systems: many programs, one machine

How do a hundred programs share one processor without knowing about each other?

A bare machine runs one program, and that program controls everything. An operating system is the program that takes charge once the machine has booted, and stays in charge. It gives each other program a slice of processor time, a private region of memory, and access to files, screens and networks, but only through requests the system can check. Those requests are called system calls.

The result is that every program gets the illusion of having a machine to itself. The core of the system, the kernel, enforces the boundaries using features built into the processor, so that one program cannot read another's memory by ordinary means.

The abstractions an operating system provides are the ones every programmer thinks in: process, file, user, permission, socket. The shell is a language for working with them: start programs, connect the output of one to the input of another, automate the lot.

The same machinery now does a new job. Containers and sandboxes are operating system features that give a program a restricted view of the machine. They are one of the ways code written by a model is run without trusting it, often together with virtual machines.

Printing is something a program asks for

A program that prints "hello" does not write to the screen. It cannot: the screen belongs to the system. At the bottom, what it does is make two requests:

system calls
write(1, "hello\n", 6)     ask the system to send 6 bytes to output number 1
exit_group(0)               ask the system to end this process (the C library's exit(0) ends up here)

Output number 1 is "standard output". Whether that is a terminal window, a file or the input of another program is decided outside the program, which never needs to know. Much of the power of Unix-like systems comes from that one decision.

What to notice
  • With a slice of 1 or 2 units, all three programs start almost at once and the short one finishes early.
  • With a long slice the system runs one program to the end before it starts the next. Music, which needs only 3 units, waits behind the download and the editor for 15.
  • Every switch has a cost that this figure does not draw. Real systems choose slices from a few milliseconds to a few tens of milliseconds as a compromise.

Central ideas

Kernel
The core of an operating system: the one program with full control of the hardware.
Process
A running program, with its own memory and its own share of processor time.
System call
A request from a program to the kernel: open this file, send these bytes, start this process.
Virtual memory
The arrangement that gives each process its own private address space, mapped onto real memory by the kernel.
File
A named sequence of bytes that outlives the program that wrote it.
Scheduler
The part of the kernel that decides which process runs next, and for how long.
Privilege
The processor's distinction between kernel code, which may do anything, and ordinary code, which may not.
Shell
A program that reads commands and runs other programs. Also the language those commands are written in.
Container
A process, or group of them, given a restricted and private view of the system.

Landmarks

  1. 1962
    Atlas and virtual memory Tom Kilburn and a University of Manchester and Ferranti team

    The Atlas computer introduced virtual memory, originally called one-level storage (paper published 1962, first production machine inaugurated December 1962), letting memories of different speeds act as a single large fast memory with automatic paging. source

  2. 1965
    Multics MIT Project MAC, Bell Labs and General Electric, led by Fernando Corbato

    After CTSS first demonstrated time-sharing in November 1961, the Multics design was presented at the 1965 Fall Joint Computer Conference (system self-hosting by the end of 1968), combining segmented virtual memory, ring protection, a hierarchical file system and an implementation mostly in PL/I. source

  3. 1969
    Unix begins Ken Thompson, Dennis Ritchie and colleagues, Bell Labs

    Ritchie dates the birth of Unix to 1969(Bell Labs withdrew from Multics in April 1969), and the system moved to a PDP-11 acquired in 1970. source

  4. 1973
    Unix rewritten in C Dennis Ritchie and Ken Thompson, Bell Labs

    Ritchie calls the 1973 rewriting of the Unix kernel in C perhaps the most important watershed in its evolution. source

  5. 1988
    POSIX IEEE

    IEEE Std 1003.1-1988, approved August 22, 1988 and published September 30, 1988, standardized the operating system interface (replacing a 1986 trial-use version). source

  6. 1991
    Linux Linus Torvalds

    On August 25, 1991 Torvalds announced on comp.os.minix a free operating system he described as a hobby, not portable, with no Minix code (version 0.01 followed in about mid-September 1991). source

  7. 2009
    seL4 verified Gerwin Klein, Kevin Elphinstone, Gernot Heiser and colleagues

    The SOSP 2009 paper reports the first formal proof of functional correctness of a complete general-purpose OS kernel, about 8,700 lines of C and 600 lines of assembler, machine-checked from specification to C (assuming compiler, assembly and hardware). source

Open problems and frontiers

  • Memory-safe kernels

    Microsoft reports about 70 percent of the vulnerabilities it assigns a CVE each year are memory safety issues, and CISA notes Rust is supported in the Linux kernel; how far existing C kernels can be moved to memory-safe languages or hardware checks is open. source

  • Verified operating systems at scale

    seL4 shows a complete kernel of about 8,700 lines of C can be proved correct, and its proofs still assume assembly, boot code, hardware and DMA are correct; proving a full general-purpose system of Linux size is open. source

  • Supply chain attacks

    On March 29, 2024 Andres Freund reported that the upstream xz repository and release tarballs had been backdoored (CVE-2024-3094), hooking liblzma to affect sshd authentication, and it was found by chance through slow SSH logins; how to detect such compromises systematically is open. source

What this means for training models

A coding agent works at this level whether or not its task is about operating systems. It runs commands, reads files, installs packages and starts processes. Terminal benchmarks test this directly: a task is described, the model works in a shell inside a container, and a script inspects the final state of the system.

The sandboxes used for all execution-based training are filed here too, because isolation is an operating system feature. Their settings (no network, limited memory, limited processes, tests out of reach) decide whether a reward can be trusted. Work on kernels themselves is rarer in open data, though kernel history is one of the largest and best documented records of change in existence.
