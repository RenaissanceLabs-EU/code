Languages and libraries: where programmers work

Why are there thousands of programming languages?

A programming language is a notation for computation together with a set of promises about what the notation means. All general-purpose languages can compute the same functions, given enough memory, a fact known as Turing completeness, so the differences between them are not about what is possible. They are about people: what is easy to say, which mistakes are impossible to make, and how much of the machine is hidden.

Every language is a position on a few trade-offs. Control over the machine against safety from your own errors. Speed of the running program against speed of writing it. Checking before the program runs against flexibility while it does. C chooses control. Python chooses ease. Rust tries to have control and safety together and pays in difficulty. SQL gives up convenience at general programming to make one kind of question effortless.

Languages come with libraries: code somebody else already wrote. A modern program is a thin layer of new code over a deep pile of existing packages, and choosing a language mostly means choosing its ecosystem. This is the level where nearly all programmers spend nearly all their time.

One algorithm, forty-four notations

Euclid's algorithm is the same idea in every language: replace the pair with the smaller number and the remainder, until the remainder is zero. What changes is how much has to be said and what the language checks. In C you declare that the numbers are unsigned integers and manage the loop yourself. In Haskell the function is two equations. In SQL it is a recursive query. In Lean it comes with a proof that it terminates.

Each language page on this site shows the same program, so they can be compared directly.

What to notice
  • Compare C with Python: the types disappear and so does the separate compile step.
  • Compare Python with Haskell or OCaml: the loop disappears, replaced by a function that refers to itself.
  • Compare anything with Verilog or SQL to see languages that do not describe a sequence of steps at all.

Central ideas

Syntax
The form of a language: what you are allowed to write.
Semantics
The meaning of a language: what happens when what you wrote is run.
Paradigm
A style of organizing programs: as steps, as objects, as functions, as rules, as queries.
Abstraction
Hiding detail behind a name, so that the user of a thing does not need to know how it works.
Turing completeness
The property of being able to express any computation at all. Nearly every general-purpose language has it.
Standard library
The code that ships with a language: text, files, collections, networking.
Package
A unit of reusable code published for others, with a name and a version.
Memory safety
The guarantee that a program cannot read or write memory it does not own. Some languages enforce it and some leave it to the programmer.

Landmarks

  1. 1957
    FORTRAN John Backus and the IBM team

    Debuted in 1957, it let a task that took as many as a thousand hand-keyed instructions be written in 47, a high-level language compiled by IBM's 1957 system. source

  2. 1960
    Lisp John McCarthy

    McCarthy's April 1960 CACM paper, the original paper on Lisp, defined a programming system through recursive functions of symbolic expressions and their computation by machine. source

  3. 1960
    ALGOL 60 An international committee including Backus, McCarthy, Naur and Perlis

    The report from the January 1960 Paris conference defined its syntax in a BNF-like metalinguistic notation, and it was reviewed and approved by IFIP TC 2 in August 1962 after a Rome meeting corrected errors. source

  4. 1968
    Go To Statement Considered Harmful Edsger Dijkstra

    Dijkstra's letter in CACM, March 1968 (pp. 147 to 148), argued that program quality falls as the density of go to statements rises and that go to should be dropped from higher-level languages. source

  5. 1991
    Python Guido van Rossum

    Van Rossum began Python in the 1989 Christmas holidays and posted it to USENET in February 1991, drawing on ABC and, for exceptions, Modula-3. source

  6. 2015
    Rust 1.0 The Rust Core Team

    Rust 1.0 was announced on May 15, 2015 with a stability commitment, offering low-level control with safety guarantees and no garbage collector or runtime. source

Open problems and frontiers

  • Memory safety without cost

    CISA reports about 70 percent of the vulnerabilities Microsoft assigns a CVE are memory safety issues and urges memory safe languages; migrating existing C and C++ code at acceptable cost and performance is open. source

  • Concurrency that is easy to get right

    Lee argued in 2006 that threads undermine clarity, predictability and determinism and that programs should instead be built from deterministic, composable components with nondeterminism added only where needed; a mainstream model that achieves this is still open. source

  • Gradual typing

    Siek and coauthors argue gradual typing needs a precise criterion, the gradual guarantee about programs that differ only in type annotations, and survey designs against it; whether mainstream languages satisfy it with good performance is open. source

  • Languages that models write well

    MultiPL-E found Codex matches or exceeds its Python performance in several other languages while language popularity and features affect results; designing languages and tooling that language models write correctly is open. source

What this means for training models

This is where almost all open training data sits, and it is very uneven. A handful of languages, led by Python, JavaScript, TypeScript and Java, account for most public code and most benchmarks. For many others there is little data and few ways to measure progress. The languages map shows the count for each.

Two problems are specific to this level. Models trained mostly on one language carry its habits into others. And libraries change faster than models are retrained, so a model will confidently call a function that was removed two versions ago. Benchmarks that are refreshed with new problems, and tasks pinned to specific library versions, are the current defenses.
