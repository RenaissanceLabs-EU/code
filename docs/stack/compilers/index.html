Compilers and runtimes: translation between languages

How does text a person can read become instructions a machine can run?

Almost nobody writes machine code by hand. A compiler is a program that translates a program: it reads source in a language people can work in and writes out the same computation in the language of a machine. The forms described on the program map (tokens, tree, types) are its first stages. The later stages choose instructions, decide which values live in which registers, and rearrange the code to run faster without changing what it means.

There are other ways to make a language run. An interpreter reads the program and carries it out directly. A virtual machine defines an imaginary processor with its own instruction set, so the same compiled program runs on any real one, which is how Java, Python and WebAssembly work. A just-in-time compiler translates the parts of a program that turn out to be used most, while it is running.

A runtime also provides services the language promises, above all memory management. A garbage collector finds memory the program can no longer reach and takes it back, which removes a whole class of errors at some cost in speed and predictability.

One fact here is easy to pass over. A compiler is itself a program, often written in the language it compiles, and compiled by an earlier version of itself. Every program you run was shaped by a chain of such tools that you have to trust.

One line, two translations

The function add(a, b) that returns a + b, compiled from C by Clang for a 64-bit ARM processor, becomes one machine instruction and a return:

ARM64 machine code and assembly
add  w0, w1, w0
ret

The same function in Python is compiled to instructions for Python's virtual machine (shown here for Python 3.9):

Python bytecode
LOAD_FAST   a
LOAD_FAST   b
BINARY_ADD
RETURN_VALUE

The C version knows at compile time that both values are 32-bit integers and emits the processor's own add. The Python version cannot know what a and b will be, so BINARY_ADD looks at them every time it runs and decides then whether to add numbers, join text or call something else. That decision, made over and over, is one of the main reasons for the speed difference between the two languages.

What to notice
  • 60 * 60 * 24 becomes a single PUSH 86400. The multiplication happened once, at compile time.
  • seconds * 7 is not folded, because this simple pass does not track what a variable holds. Production compilers do, and would fold the entire program down to one print.
  • Both versions print the same thing. An optimization that changed the output would be a compiler bug, and such bugs do exist.

Central ideas

Compiler
A program that translates source code into another language, usually machine code, before it runs.
Interpreter
A program that carries out source code directly, without producing a separate translation.
Intermediate representation
The compiler's internal form of a program, between the source tree and machine code, where most optimization happens.
Optimization
Rewriting a program to use less time or memory while preserving its meaning.
Virtual machine
An imaginary processor implemented in software, with its own instruction set (bytecode).
Just-in-time compilation
Compiling parts of a program to machine code while it is already running.
Garbage collection
Automatic recovery of memory that the program can no longer reach.
Linker
The tool that joins separately compiled pieces, and libraries, into one runnable program.
Bootstrapping
Building a compiler with an earlier version of itself.

Landmarks

  1. 1952
    A-0 system Grace Hopper

    The A-0 converted symbolic mathematical code into machine code by retrieving subroutines stored on tape by call number, and the Computing History archive calls it her first compiler (whether it counts as a compiler or a linker-loader is debated). source

  2. 1957
    FORTRAN compiler John Backus and the IBM team

    The IBM Mathematical Formula Translating System debuted in 1957 (work began in 1953 to 1954), and its optimizing compiler produced code that ran nearly as fast as hand-written code. source

  3. 1960
    ALGOL 60 report Backus, Bauer, McCarthy, Naur, Perlis and others, editor Peter Naur

    The report that came out of the January 1960 Paris conference (revised 1962) defined syntax with a BNF-like metalanguage, a notation with angle-bracket names, ::= and |. source

  4. 1984
    Reflections on Trusting Trust Ken Thompson

    Thompson's Turing award lecture, published in CACM vol. 27, no. 8 (August 1984), showed a compiler can carry a Trojan horse that reinserts a login backdoor whenever it is recompiled, even after the source is cleaned, so inspecting source alone cannot establish trust. source

  5. 1991
    Static single assignment form Ron Cytron, Jeanne Ferrante, Barry Rosen, Mark Wegman and Ken Zadeck

    The paper (Brown technical report March 1991) gave efficient algorithms using dominance frontiers to build SSA form and the control dependence graph, the program representation most modern optimizers use. source

  6. 2004
    LLVM Chris Lattner and Vikram Adve

    The CGO 2004 paper presented a compilation framework built on a low-level SSA-based representation that enables analysis and transformation at compile time, link time and run time, and it became shared compiler infrastructure for many languages. source

  7. 2009
    CompCert Xavier Leroy

    Leroy's July 2009 CACM article described CompCert, a compiler from a large subset of C to assembly whose correctness (the generated code behaves as its source) is proved in the Coq proof assistant. source

Open problems and frontiers

  • Automatically discovered optimizations

    Souper, a synthesizing superoptimizer for LLVM, produced a Clang binary about 4.4 percent smaller than LLVM's own and suggested optimizations later implemented by hand; making superoptimization cheap and general enough to run in production compilers is open. source

  • Compiling for accelerators

    MLIR (2020) proposes a reusable, extensible infrastructure to reduce fragmentation and ease compilation for heterogeneous hardware and domain-specific compilers; how to share optimizations across the many accelerator targets is open. source

  • Learned compiler heuristics

    MLGO replaced LLVM's inlining-for-size heuristics with learned models that cut code size by up to 7 percent and has been merged into LLVM; extending learned decisions to more passes while keeping results reliable and reproducible is open. source

What this means for training models

The compiler is the most used verifier in practice. "Does it build" is a faster and stricter check than most tests, and its error messages are the richest feedback a model gets during a coding session.

Translation between languages is a long-standing benchmark task, usually judged by running the translated program against tests. Work inside the compiler, such as choosing optimizations or generating intermediate code, has datasets too, though far fewer. It also has one unusual property: the output can sometimes be checked for equivalence with the input, which is a guarantee that a test suite cannot give.
