## 1. What the PSF license allows (read from the license file on disk and from the docs page)

- Local file: the Python 3.9.6 install ships `LICENSE.txt` (13,925 bytes, sha256 `599826df92bfdcd2702eac691072498bb096c55af04ee984cf90f70ed77b5a70`). It states that "Python software and documentation are licensed under the Python Software Foundation License Version 2", and that "Some software incorporated into Python is under different licenses. The licenses are listed with code falling under that license." It also says that, starting with Python 3.8.6, examples, recipes and other code in the documentation are dual licensed under PSF License Version 2 and the Zero-Clause BSD license (this concerns documentation code, not the `Lib` tree we used).
- PSF License Version 2, clause by clause (local text, confirmed against https://docs.python.org/3/license.html, which currently shows the Python 3.15.2 documentation page): a nonexclusive, royalty-free, world-wide license to reproduce, analyze, test, perform and display publicly, prepare derivative works, distribute and otherwise use Python alone or in any derivative version, provided the PSF license agreement and the PSF copyright notice are retained (clause 2); a derivative work made available to others must include a brief summary of the changes (clause 3); "AS IS", no warranties (clause 4); no liability (clause 5); automatic termination on material breach (clause 6). The docs page adds that the license does not permit using PSF trademarks to endorse products.
- SPDX identifier `PSF-2.0` ("Python Software Foundation License 2.0"), https://spdx.org/licenses/PSF-2.0.html.
- Consequence for a dataset of stdlib files: it is a permissive license. Redistribution of the files, including inside a dataset, is allowed if the license text and copyright notice travel with the data and any modification is summarized. The example ships `LICENSE` verbatim, keeps the original headers, and summarizes the scrubber's changes in the card.
- Third-party code inside the stdlib is under other licenses. The docs page lists BSD-style, MIT, Apache 2.0, zlib and other notices for incorporated software. In the `.py` files we scanned, the header regex found 2 Apache-2.0 files (`profile.py`, `pstats.py`), 1 file stating MIT or Apache-2.0 (`wsgiref/validate.py`), 13 files with an "HPND-style" permission notice (for example `asyncore.py`, `asynchat.py`, `http/cookies.py`, `xmlrpc/client.py`, `xml/etree/*`, `logging/config.py`, `logging/handlers.py`, `trace.py`, `uu.py`) and 1 BSD-style (`optparse.py`). The 14 non-SPDX-mapped ones were excluded by the gate pending human review. This is a regex over the first 6,000 characters of each file, so a file with a license notice later in the text, or no notice, is treated as PSF-2.0. The tree-level statement in LICENSE.txt is the only authority we have for those.

## 2. Redistributing training examples versus publishing a metadata catalog

- Redistributing code (what the example dataset does): copies of the files, or derived records that contain their text (every `code_corpus` record, and `docstring_pairs` which contain function text), are copies or derivative works of the source. The licenses of the files apply to them: keep notices and license texts, summarize changes (PSF-2.0 clause 3), meet attribution terms (Apache-2.0, MIT, BSD), and observe copyleft terms where files carry them (GPL-family, MPL, LGPL, EPL: the BigCode material below says The Stack v1.1 dropped MPL, EPL and LGPL for this reason). A per-file `license` field is the minimum metadata that lets downstream users comply.
- Publishing a catalog of resource metadata (what the Renaissance Labs catalog does: names, links, size, license of the original, summaries): contains facts about resources, not the resources' content. It does not copy the code, so the code licenses are not triggered by the catalog itself; the catalog still has to report each resource's license correctly and link to the original. Quoting descriptions word for word from a card is a separate copyright question for the text, so summaries are written in our own words.
- Dataset-level versus file-level licensing: a compilation can carry its own terms for the compilation, but cannot relicense the parts. Hence `license: other` plus `license_name` and `license_link` on the card, and per-file license fields.
- Gated or "agreement" datasets (The Stack family) add access terms on top of the file licenses; those are the dataset publisher's terms, not the code authors'.

## 3. How The Stack and BigCode handle opt-out and per-file license metadata

Read on 2026-11-25:

- https://www.bigcode-project.org/docs/about/the-stack/ : developers can ask for their repositories to be removed by opening an issue in the BigCode opt-out repository, after checking with the "Am I in the Stack" tool; requests can cover all repos, selected repos, specific commits or issues; ownership is verified; validated requests are stored so the code stays out of later versions; removals are planned about every 3 months (the page says this may change). The Stack includes only permissive-licensed code; v1.0 included MPL, EPL and LGPL, v1.1 excluded them and expanded the permissive list to 193 licenses; users must follow each file's original license including attribution; provenance is given for each data point; a list of SPDX identifiers is published. Users must agree to use the most recent allowed version so removals are applied; if BigCode stops maintaining the dataset it plans to stop distributing it in its current form.
- https://huggingface.co/datasets/bigcode/the-stack-v2 : "a collection of source code from repositories with various licenses"; users must follow the original licenses; the permissive list is compiled from Blue Oak Council and ScanCode categories; repo-level license data comes from GH Archive, and for repos lacking it (the card says 96.93%) file-level licenses are detected with ScanCode Toolkit and propagated to files sharing a base path with the license file; each record has a `license_type` (`permissive` or `no_license`); the card says all files are permissive or unlicensed to the best of its knowledge; the data comes from Software Heritage and the dataset holds SWHIDs, with bulk content download requiring an agreement with Software Heritage and Inria; opt-out removals are applied; the card warns that data "may contain sensitive information such as emails, IP addresses, and API/ssh keys" and that removal requests go to the contact address on the card; access is gated behind accepting conditions.
- Paper: StarCoder 2 and The Stack v2 (arXiv 2402.19173, submitted 2024-02-29, 66 authors, first author Anton Lozhkov) says it builds on the Software Heritage archive, 619 programming languages, and releases the SWHIDs. The abstract text we read did not mention opt-out.
- Tooling repo https://github.com/bigcode-project/bigcode-dataset has directories `pii`, `near_deduplication`, `decontamination`, `language_selection`, `preprocessing` (line length, alphanumeric ratio and other filters). The `pii` README describes NER-based and regex-based detection, detect-secrets with extra filters, a gibberish detector, and placeholder redaction (IP addresses replaced with random synthetic private IPs). The repo itself is Apache-2.0. The page we read states no license detection code in that repo.
- Lesson used in the example: keep per-file license metadata, keep provenance sufficient for removal requests (path, source version, hashes), allow later removals by versioning, and document the opt-out channel on the card. The example has no opt-out channel because the source is the PSF's own stdlib; a real dataset of third-party repositories needs one.

## 4. Hugging Face dataset card spec

- https://huggingface.co/docs/hub/datasets-cards : the card is the dataset repo's `README.md`; YAML metadata sits between `---` lines at the top; keys include `language`, `license`, `pretty_name`, `tags`, `task_categories`. License keywords from the table at https://huggingface.co/docs/hub/repositories-licenses are shown on the page. Tags can force a modality or associate a library.
- https://github.com/huggingface/hub-docs/blob/main/datasetcard.md : key list read: `language`, `language_details`, `license`, `license_name`, `license_link`, `license_details`, `tags`, `annotations_creators`, `language_creators`, `pretty_name`, `size_categories`, `source_datasets`, `task_categories`, `task_ids`, `configs` (each with `config_name` and `data_files` as split/path), `dataset_info`. For licenses not in the list: `license: other` with `license_name` and `license_link`. The page gives `size_categories` examples (`n<1K`, `100K<n<1M`) but not the full set.
- https://huggingface.co/docs/hub/datasets-manual-configuration : `configs` with `config_name` (required even for one subset) and `data_files` list of `split` and `path`; globs allowed; multiple subsets allowed. The example uses this for the two record types.
- The license table has no `psf-2.0` entry (fetched 2026-11-25), hence `license: other`.
- Installed `datasets` 4.5.0 loaded both configs from `out/` via the card with correct split counts (RUN_LOG.md). That shows the YAML works for local loading, not that the Hub accepts it.
- CLI for the push script: huggingface_hub 0.36.0 installed here, `hf` entry point with `hf repo create`, `hf repo tag create`, `hf upload` (read from `--help`); the current docs page https://huggingface.co/docs/huggingface_hub/guides/cli uses the group name `hf repos` (`hf repos create`, `hf repos tag create`). The docs page did not mention `huggingface-cli`; the 0.36 package still declares a `huggingface-cli` entry point. Python API signatures `create_repo`, `upload_folder`, `create_tag` read from the installed package.

## 5. Pipeline design notes (what the run showed)

- 682 `.py` files, 674 readable within the caps, 588 released. Near-dedup removed 44 files, all codec modules under `encodings/` (shared boilerplate; Jaccard 0.80 to 0.98). Clusters are transitive.
- Group split gave 523 / 16 / 49 files for train / validation / test: grouping by hash makes small corpora lumpy.
- The stdlib has no top-level `test` directory on this machine (Apple's Xcode Python framework omits it); only `sqlite3/test` and `tkinter/test` exist. Test pairing was therefore dropped.
