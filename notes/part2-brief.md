# Part two brief: "How to train language models for code" (2026-11-25)

Shared by the research passes. Read notes/rebuild-brief.md first (house rules: verify everything from sources fetched now, never invent, American English, no em dashes or en dashes used as punctuation, plain direct copy, no hedging filler).

The site code.renaissancelabs.eu has a conceptual part one (what a program is, the stack, languages, the world). Part two is a structured learning path, "How to train language models for code", for two audiences: readers who need a clear introduction and practitioners who want to inspect resources, prepare data and run an experiment. Success criterion: a reader leaves knowing what capability they want to train, which datasets and tools to consider and why, how to build a documented Hugging Face dataset, and how to run and evaluate a first training experiment.

Pages of the path (each research pass feeds some of them):
1. Choose a capability: completion and fill-in-the-middle, instruction following, debugging and repair, repository-level editing, test generation, tool use. Compare pretraining from scratch, continued pretraining, SFT, and preference or execution-based feedback (RL). Choose by objective, data and compute.
2. Why this data: raw code, documentation, instruction-response pairs, issue-patch pairs, tests, execution traces, synthetic examples; the learning signal each gives; tradeoffs of volume, quality, diversity, difficulty, relevance.
3. Datasets directory: a curated starting selection by purpose and stage; contents, capabilities, languages, format, size, limitations, links to the original source and the Hugging Face page, evidence for any claim of popularity. Distinguish training datasets, evaluation benchmarks and interactive environments.
4. Build a dataset: worked example from source selection to a versioned Hugging Face dataset: provenance, license review, filtering, dedup, secret and personal-data removal, formatting, splits, leakage between related repositories, benchmark contamination; example records, schema, preprocessing code, dataset card. Distinguish publishing a catalog of resource metadata from redistributing training examples.
5. Tools directory by workflow role: collection, processing, tokenization, training, experiment tracking, execution, evaluation. What each does, when it is useful, how it connects to other steps. A minimal setup for a newcomer and options for larger experiments.
6. Reproducible training recipes: at least one approachable fine-tune of an existing model on a small, carefully prepared code dataset: objective, base model, dataset, hardware assumptions, configuration, commands, evaluation. Label compute estimates and expected outcomes as estimates unless measured.
7. Evaluation as part of training: held-out evaluation, execution-based correctness, repository-level tasks, regression checks, benchmark limits and contamination, executing generated code in isolation.
8. Link to part one: program text, structure, types, execution, tests, proofs, changes mapped to the training data and feedback signals they can provide.
Everywhere: mark verification dates (use "2026-11-25") and distinguish established practices from emerging and experimental ones.
